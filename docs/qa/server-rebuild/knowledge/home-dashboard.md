# Home dashboard — behaviour knowledge

_Extracted 2026-11-06 from three sources: server develop @ `eeecf9ddb` (Release/79) code + `schema.graphql`; the legacy suites — this catalogue feature (SP-12, "REST / UI only") has no `server-api/src/functional-api/<area>/` folder, so the proof is the 0 own + 31 cases of other server-api areas (`graphql-guard` 6, `roleset` 16, `communications` 8, `journey` 3 — counted in the dossier § 2) and 6 client-web Playwright walks (`memberships/view-home-dashboard-*` 2, `home-menus` 3, `support-navigation` 1) that exercise it; the specs, issues and docs listed in § Sources. Scope: the `me` surface the dashboard and top navigation read (my spaces and memberships with their ordering, my pending invitations and applications, my notification counts, my conversations), the dashboard fields on other roots (`Space.activityScore`, the activity-view and home-space settings), the non-activity home, and the url-resolver branches for the "my" pages and the navigation targets. `me.user`, `me.mcpApiKeys`, `me.accountDeletion` belong to ID-3, 038 and account deletion. WHAT and WHY only — no mutations, fixtures or request params. Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". Evidence paths are relative to the server repo unless prefixed `test ›` or `spec ›`._

_Review load: 9 findings · 1 unknown-why row · 7 untested rows (gaps) · 20 constants to tick · 6 open questions. Manual points sit in five places: the Findings, the `unknown-why` rows, the `untested` rows (repeated under Gaps), the "product must rule?" column of the constants, and the Open questions._

## Where this lands in the new core

The catalogue puts SP-12 on the **`viewer` document** (slice 4–5): the `me` root becomes `viewer`, and the pieces it aggregates today are reshaped around it — community/roleSet become credentials on the space, so "my memberships" (HOME-03/04) is a credential read on the viewer with the hierarchy derived from the space document; applications and invitations become one `membership_request`, so the four partitioned lists and their counts (HOME-05…10) collapse into one typed list with a state filter — F6 (finalized rows) and F4 (one bad row fails the field) should be settled before that list is designed; notification kinds become registry rows and counts are computed at read (HOME-13 — the badge/list asymmetry must be decided, not carried over); chat goes browser → Synapse, so `me.conversations` (HOME-14) has no stated successor on the server; activity stays append-only and partitioned with counts at read, which is where `activityScore` and the recent-spaces ordering (HOME-11/12/15, ACT-70…72) move — the new core should own the 30-day and 7-day windows rather than leave one to the client (F8, F7); preferences become `user_settings` attribute rows (HOME-16/17). `urlResolver` becomes `resolve(url)` with IDs and URLs preserved through aliases — the reserved-but-unresolvable words (HOME-22, F5) and the "everything else is a space" assumption (HOME-23) are the two rules to make explicit in that grammar. The UI is kept, so HOME-30…34 stay as written and are the acceptance walks for the rewritten client.

## Findings (sources disagree, or likely defect)

1. **Hierarchical memberships drop subspace memberships whose parent the person is not in (HOME-04).** Code: children are attached only under a top-level space that is itself in the caller's list (`me.service.ts:288-341`); the flat list has the row. Test: none (both walks seed the parent membership too). Spec: none. The client's dashboard tree and the home redirect read the hierarchical view. Ruling: is an L1-only member meant to see that space on the dashboard tree? If yes, defect; if no, record the rule and say why.
2. **Recent spaces can return fewer than asked (HOME-11).** Code: raw activity is cut at `limit × 2` before the membership filter — the code's own TODO (server#3626, "magic number, should not be needed"; the issue's `RecentJourneys` AC is still unticked). Test: none. Spec: 024 relies on this list for Section 1. Ruling: fix the overfetch/underfetch (fetch by membership, then cut) or accept.
3. **Unread badge counts rows the person cannot see (HOME-13).** Code: raw count vs filtered page. Test: SRA cases assert shape only. Spec: server#6699 records the residual as accepted. Ruling: keep (badge = "something happened") or align (badge = visible unread) — the new core computes counts at read and needs one answer.
4. **One unresolvable pending row fails the whole pending list (HOME-10).** Code: `EntityNotFoundException` thrown inside the loop. Test: none. Spec: none. Same failure shape server#6699 fixed for notifications. Ruling: hide-and-log the bad row (as notifications do) or keep the hard failure; also whether such rows can exist after the cascade fixes (W4 register has no row for orphan invitations — check).
5. **Six reserved route words cannot be resolved (HOME-22).** Code: `UrlPathBase` lists `about, profile, contact, landing, identity, flows`; `resolveBaseRoute` has no case for them → NOT_FOUND "Unknown base route". Client (stale clone): `TopLevelRoutePath.Profile` exists; no consumer found. Test: none. Ruling: are these routes live in the client (then the resolver must answer them) or only name reservations (then record that)?
6. **Pending lists include finalized rows unless the caller filters (HOME-08).** Code: no state predicate without `states`. Test: `application` › "should return correct membershipUser applications" filters `state == 'new'` itself, which only works because finalized rows are present. Spec: 024 FR-014/015/018 count "pending" rows. Ruling: should the server default to open rows (the badge then matches the spec without a client filter), or is the client's `states` argument the contract? Also decide the count's meaning for the `membership_request` list.
7. **`activityScore` on an unreadable space errors the field (HOME-15).** Code: the loader returns a `ForbiddenAuthorizationPolicyException` for a denied key; `activityScore` is `Int!`, so the error nulls the parent object — the same shape as #6699. Also the 7-day window is fixed in the loader while `exploreSpaces` takes a caller-supplied `daysOld` ("that alignment is the caller's, not enforced here"). Test: helpers exist (`visual.request.params.ts:128-170`), no spec imports them; the activity-logs plan cites an untracked `dashboard-activity-authorization.it-spec.ts` that is on no branch. Ruling: return 0/null for unreadable spaces, and fix the window to the registry; write the missing spec.
8. **The 30-day "Last Active In" window exists only in the client (HOME-12).** Code: no date predicate. Spec: 024 FR-005 states the window; the contract deliberately left it client-side. Test: none. Ruling: in the new core, does the server own the window (so API consumers get the same list) or the client?
9. **Home-space pin: client L0-only, server any credentialed space (HOME-17).** Code: `user.settings.home.space.validation.service.ts` checks the credential only (CM-20). Spec: 024 FR-004 restricts the pin to L0 "consistent with the existing home-Space picker". Test: none. Ruling: enforce L0 on the server or record the client as the gate.
