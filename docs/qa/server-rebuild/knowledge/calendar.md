## Where this lands in the new core

Per the rebuild briefing (`plan.md` § 1, catalogue), the calendar is a child of the space document: events become rows owned by the space with the creator as an ordinary row fact (the matrix already treats `createdBy` grants as per-row, `access-matrix.md:2563`), rights resolved at read time from the space's membership instead of a stored policy per event, calendar and timeline (which removes the 247 empty-policy rows of crosscheck F3 as a class). The whole-day contract (EVT-17) is a data-shape convention recorded in ADR 0001 and must be carried into the new schema as-is — ideally as a real date column for whole-day events rather than a UTC-midnight instant. Three facts here should shape the model: (1) the roll-up is one level deep and L0-only today (EVT-10, F-3) — the new core should decide depth explicitly; (2) date validation lives only on read (EVT-19, F-4) — move it to write; (3) the ICS endpoint is a session-authenticated REST read with redirect semantics (EVT-22) — decide anonymous access before porting. Error texts and link formats are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **Anonymous ICS download (EVT-22).** Code: the REST endpoint redirects a visitor to `/login` and a signed-in actor without read to `/restricted`. Test: two todo cases say "Per spec (User Story 3): unauthenticated users should be able to download .ics files". Spec: 023 is silent; the originating spec (#5860 era) is not in the repo. Ruling: is the ICS file public for public spaces (then the redirect is a defect) or authenticated-only (then the todos are wrong)?
2. **Stale "Bearer not accepted" annotation (EVT-21/22).** Code: `RestGuard` accepts cookie session, non-interactive login and Hydra bearer (FR-025 comment). Test: `calendar-event.it-spec.ts` skips one case and parks 7 todos claiming Bearer gets a 302, while `calendar-event-wholeday-timezone.it-spec.ts` downloads with Bearer as `space.admin` and gets 200 with the right dates. Ruling: un-park the 7 ICS todos (content type, structure, location, markdown strip, VALUE=DATE, datetime) — they are runnable today.
3. **Roll-up depth (EVT-10).** Code: only `level = L1` children of the queried space roll up, so an L0 shows its L1 events and nothing else, and an L1 calendar never shows L2 events; the comment says how to widen it. Schema/setting text: "events from Subspaces are visible on this Space calendar". Test: none (the only list case reads own events). Ruling: is one level the product rule?
4. **Dates validated on read, not on write (EVT-19).** Code: a timed event with `durationMinutes 0` (or a start after its end) is created and updated without complaint; every subsequent read of its link fields or ICS fails with "Invalid calendar event date range" (and the create mutation's own response errors when the client selects the link fields, which is how B1's "broke creation outright" was observed). Spec 023 only says what to accept. Ruling: validate at write and treat the read-time check as a safety net.
5. **`Calendar.event(ID)` has no per-event read check (EVT-12).** Code: the field guards READ on the calendar and returns the event; `Calendar.events` and `lookup.calendarEvent` check READ on the event. Harmless while every event's policy is a superset of its calendar's, but inconsistent. Ruling: align or drop the field.
6. **Duration triple is caller-asserted (EVT-03/13).** Code stores `durationMinutes`, `durationDays` and `multipleDays` as sent; nothing checks that days × 1440 = minutes or that multipleDays matches. Spec 023 FR-003/FR-011 make the client derive them. Test C1 pins "durationDays is derived and must never be added on top". Ruling: accept client-derived, or derive server-side in the new core.
7. **Creator rights outlive membership (EVT-24).** Matrix: `creator-former-member` keeps create/update/delete on the event. Code: the rule is keyed on `user-self-management:<createdBy>` with no membership condition. Spec: none. Ruling: intended?
8. **Dangling creator (EVT-25).** `createdBy` is a bare uuid with a TODO (server#4529); deleting the user leaves the id and the creator rule. `createdBy` resolves to null. Ruling: cosmetic, or clear on user deletion?
