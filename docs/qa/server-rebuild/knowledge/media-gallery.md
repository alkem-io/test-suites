# Media gallery and references — behaviour knowledge

_Extracted 2026-11-06 from three sources: server develop @ `eeecf9ddb` (Release/79) code + `schema.graphql`; the legacy suites — this catalogue feature (CT-9) has no `server-api/src/functional-api/<area>/` folder (`references/` holds request params only), so the proof is the cases of other areas that exercise it: `callout/post/post-on-callout` (4 reference cases), `storage/uploads` (12 upload-on-reference cases), `storage/auth/*` (reference-document rows of the document-auth decision table, cross-referenced) and 1 client-web walk (`user-profile/view-profile-information`); **no case anywhere touches a media gallery** (`addVisualToMediaGallery`, `deleteVisualFromMediaGallery`, `mediaGallery` and `updateReference` have 0 hits in server-api, client-web and lib). Scope: the media-gallery framing of a callout and its items (creation, positions, limits, removal, who may), and references on profiles (create, update, delete, file on a reference, address validation). Buckets, documents, uploads limits and document access are the storage area and the access matrix; the visual slot rules (formats, sizes, ratio, upload rights) are visual.md VIS-04…08 and VIS-16/17 — cross-referenced, not redone. WHAT and WHY only — no mutations, fixtures or request params. Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". Evidence paths are relative to the server repo unless prefixed `test ›` or `spec ›`._

Manual points sit in five places: the Findings, the `unknown-why` rows, the `untested` rows (repeated under Gaps), the "product must rule?" column of the constants, and the Open questions._

## Where this lands in the new core

The catalogue puts CT-9 on **`storage_bucket`, `file`, `file_ref`** — content-addressed blobs, uploads straight to the file container by signed token (slice 4–5) — and the briefing folds callout, contribution and post into **one recursive `post` with a kind**. The gallery therefore stops being a side entity on a framing and becomes a post of kind "media gallery" whose items are ordered `file_ref`s; every rule above survives as a behaviour, but three facts should shape the model: (1) the item is a slot first and a file second today (MED-03/09, F1) — in a content-addressed store the item *is* the file, so "add item" and "upload" collapse and the contribution event has one natural trigger; (2) position is a nullable int with no uniqueness and no reorder (MED-06, F8) — the new post needs an explicit ordering contract; (3) the creator rule is a stored policy row (MED-08) and stored authorization policies disappear — it becomes a computed rule on the post's `created_by`. References have no stated successor beyond `file_ref`: a reference is a named outbound link on a profile (MED-21/22) that may also point at an owned file (MED-25); the new profile needs a typed link row with a validated address (F3) and a uniqueness rule that holds on every write path (F4). Uploads, the GDPR-motivated anonymous read of profile documents and the F1 direct-bucket exposure are the storage area's to carry over.

## Findings (sources disagree, or likely defect)

1. **The contribution event fires on slot creation, not on upload (MED-09).** Code: `addVisualToMediaGallery` reports; `uploadImageOnVisual` does not. Spec 039 FR-001: "when a user successfully uploads a visual"; edge case: "The contribution should only be reported on successful upload completion"; US1-AS2: "each upload generates its own contribution event". Test: none. Consequence: an empty slot counts as a contribution; re-uploading into a slot counts nothing. Ruling: move the report to the upload (then rebaseline the Kibana numbers) or amend the spec.
2. **Any visual kind can be added as a gallery item (MED-04).** Code: the input takes the whole `VisualType` enum and the slot copies that kind's bounds (an `avatar` item is 190–410 px square). Description: "e.g. MEDIA_GALLERY_IMAGE, MEDIA_GALLERY_VIDEO". Test/spec: none. The client (stale clone) has a `mediaGalleryVisualType.ts` guard — not read. Ruling: refuse non-gallery kinds server-side, or record that the client is the gate.
3. **No address validation on references or links (MED-22).** Code: `uri` is `MaxLength`-only on `CreateReferenceInput`, `UpdateReferenceInput` and `CreateLinkInput`; `updateVisual.uri` has the same gap (VIS finding 7). Test: every case sends `https://testref.io`. Spec: none. A reference can carry `javascript:` or free text that the client renders as a link. Ruling: validate (http(s) / mailto, or an Alkemio document URL) on the server, or record the client as the gate — and decide for the new `file_ref`/link row.
4. **Duplicate reference names are refused on one path only (MED-21/23).** Code: `profile.service.ts:596-602` checks on `createReferenceOnProfile`; `updateReferences` (bulk through `updateProfile`) and `createProfile(referencesData)` do not. Test: none. Ruling: is the name unique per profile (then enforce everywhere, and migrate duplicates) or not (then drop the single check)?
5. **Removing an item or a reference leaves the file behind (MED-05/24).** Code: `deleteVisual` and `deleteReference` delete the row and policy, never the document; the storage suite pins "file is available after related reference is deleted" as a feature. Spec: none. For a gallery the file stays in a bucket nobody can list from the UI. Ruling: intended (files are bucket-owned; the W4 orphan rows apply) or a leak to clean on removal.
6. **Removing an item needs "update" on the gallery, not "delete" (MED-05).** Code: both gallery mutations gate on `UPDATE` of the gallery; the visual's own policy (which inherits DELETE for managers) is not consulted. Everywhere else on the platform a removal needs DELETE on the thing. Test/spec: none. Ruling: align or record.
7. **The ratio column cannot hold the gallery range (MED-07).** Cross-reference visual.md finding 4 (`aspectRatio decimal(3,1)` vs allowed 100 and an unbounded computed ratio) — decided there, not here.
8. **No cap, no unique position, no reorder (MED-06).** Code: nothing limits item count; `sortOrder` accepts duplicates and negatives; `updateVisual` has no `sortOrder`. Test/spec: none; PR #5798's intent unread. Ruling: product to state the maximum items per gallery and whether reordering is a feature — both are rebaseline rows for the new post kind.

## Gaps (no legacy case)
