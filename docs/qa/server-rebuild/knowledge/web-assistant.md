# Web AI assistant — behaviour knowledge

_Extracted 2026-11-06 from three sources: server develop @ `eeecf9ddb` (Release/79) code + `schema.graphql`; the legacy suite — this feature (catalogue AI-3, verdict absent) has **no server-api folder of its own**, so the proof is one `platform-roles` capability row (A11 `updateAssistantActorCapabilities`, 14 roles) and two client-web walks (`platform-roles/feature-roles-offers.spec.ts`, `authz-admin-guard/platform-global-roles.spec.ts`); the specs, contracts and docs listed in § Sources. Scope: what the **server** guarantees for the web AI assistant — the access privilege, the budget resource, the `virtual-assistant` actor and its admin grant, the per-user grant, the capability classification and gate, delegated MCP calls, the bootstrap of the assistant's MCP key, and the `inputCreator` query the catalogue files here. The conversation itself (history, confirmation, proposal TTL, reply language, metering) lives in the private `assistant-service`, which is not available locally — those are open questions, not rules. WHAT and WHY only — no mutations, fixtures or request params. Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". Evidence paths are relative to the server repo unless prefixed `test ›` or `spec ›`._

## Where this lands in the new core

The catalogue lands AI-3 at "agent (kind assistant); assistant-service unchanged" (slices 10–12, verdict absent, "owned by assistant-service tests; confirm"). The `virtual-assistant` singleton becomes an `actor` row of kind assistant with its admin grant as attribute rows; the user's grant becomes `user_settings` attribute rows (AST-10); the access privilege becomes a platform feature credential scoped by target type (AST-01, ENT-36 pattern); stored authorization policies and resets go, so AST-07's "registered may read / POA manages" is a read-time rule. The MCP host, the capability gate and the delegation trust anchor (AST-11…AST-16) are the one surface the deck leaves unchanged — assistant-service keeps calling the server as the assistant actor with the on-behalf-of header — so the new core must carry the gate, the classification map, the key bootstrap and the attribution join keys across the cutover unchanged, and the ID-6 continuity item (keys must survive or re-mint) applies to the assistant's key as well. Two facts should shape it: (1) the classification map, the seeded grant and the contract disagree on tool names today (F-2/F-3), so the registry of capabilities should be the single source and the grants should be derived; (2) the budget is a server resource with no server-side meter (F-4) — if metering is to be rebuildable after a cache loss (FR-028), the counter needs a home the deck has not named.

## Findings (sources disagree, or likely defect)

1. **Spec and migration describe a retired access design (AST-04).** Spec 004 FR-027(a): `GLOBAL_ADMIN` baseline + `PLATFORM_ASSISTANT_ACCESS` role → `assistant-access` credential. Code: the rule names `feature-virtual-assistant` only (027 T076/T077); migration `1780600000000` still inserts the dead role on already-bootstrapped databases, and the doc comment at `platform.service.authorization.ts:235-242` still describes the old design. Test: the client walk proves the feature-role behaviour. Ruling: amend 004 FR-027(a), drop or neutralise the migration's role row, fix the comment.
2. **The seeded actor grant names a tool that does not exist (AST-08).** Migration: `update_whiteboard_content` off, `import_whiteboard_scene` absent. Registry: `import_whiteboard_scene` exists, `update_whiteboard_content` does not. Harmless at the gate (absent ⇒ off) but the a11 read-back pins the stale row and an admin UI would show a phantom toggle. Ruling: migrate the grant to the live names.
3. **Classification map vs contract (AST-11).** Contract `assistant-authority.md:42-57`: `update_whiteboard_content` WRITE_DESTRUCTIVE, every other tool READ, "each side ships a parity test asserting its local classification equals this table". Code: `import_whiteboard_scene` WRITE_ADDITIVE, no `update_whiteboard_content`, no WRITE_DESTRUCTIVE entry at all. Ruling: update the contract (and assistant-service's copy) to the code map, or vice versa; confirm the parity test exists on both sides.
4. **Budget is resolved but never enforced on the server (AST-05/06).** Code: the resource returns the limit; usage is hard-coded 0 (ENT-13); no turn or token record exists. Spec: FR-027(b)/FR-028 enforcement and persistence "not yet implemented"; ENT F-1: the free tier is never issued, so `tokensPerMonth` is `null` for every non-plus user and the assistant applies its own default. Ruling: where the monthly counter lives in the rebuild, and whether a plan-less user is meant to get the assistant-service default rather than the signed-off 1M free tier.
5. **`inputCreator` is not an assistant capability (AST-18).** Catalogue AI-3 lists it as one of the feature's two root fields; the code is a template/duplication helper with no assistant involvement. Ruling: re-file it (templates area) so the AI-3 verdict is computed on the real surface.
6. **The capability surface is readable by anonymous callers (AST-11).** Code: `platformCapabilities` has no guard, so the MCP tool list (names, descriptions, kinds) is public while the assistant is restricted to a feature role (FR-005 "only to authenticated users"). Ruling: accept (the surface is documentation) or gate on registered.
