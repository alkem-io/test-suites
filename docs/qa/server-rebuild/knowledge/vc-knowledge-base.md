## Where this lands in the new core

The catalogue puts AI-1 at "agent (kind vc) + ai_engine registry" (slices 10–12, verdict partial; W2 journey 9 parked while VCs are hidden in the client). In the rebuild a VC is an `actor` row of kind vc, its knowledge base becomes an ordinary post container (callout/contribution/post collapse into one recursive `post` with a kind — the knowledge base is then just a post tree owned by the VC), its persona is a row in the `ai_engine` registry, and the stored authorization policies plus every reset disappear, so VCK-05/VCK-15 become read-time rules on the VC's visibility and its one privacy flag. RabbitMQ and the matrix-adapter go; chat moves browser → Synapse, so VCK-26…VCK-34 (mention parsing, thread binding, reply posting, interaction records) need a new home — the deck says nothing about who summons a VC and posts its answer once the server no longer sees Matrix traffic, and that is the biggest open design point this table surfaces. Three facts should shape it: (1) summoning today is ungated (F-1), so the new core must decide whether a VC answers only where it is a member; (2) six stored VC attributes have no server behaviour (F-3) and should be dropped or implemented, not migrated blindly; (3) the ready stamp (VCK-11/12) is the only VC state the engine writes back, and the subscription that carries it is on the retire list.

## Findings (sources disagree, or likely defect)

1. **Summoning a VC is ungated (VCK-31).** Code: `room.mentions.service.ts:72-116` resolves the mention by nameID and invokes without checking that the VC is a member of the space, readable by the poster, or even enabled for the account; the space VC flag (ENT-30/VCK-36) gates role assignment only. Test: none. Spec: 040 speaks only of conversation membership. Ruling: must a VC be a member of the space (or at least readable by the poster) to be summoned?
2. **Two VC mentions in one message ask the first VC twice (VCK-27).** Code: the loop creates the interaction for the first mention and then invokes `vcInteraction.virtualContributorID` on every iteration. Test: none. Spec: none. Ruling: defect (invoke each mentioned VC once) or rule (one VC per thread, extra mentions ignored)?
3. **Six stored VC attributes have no server effect (VCK-16…19).** Code: `promptGraphEditingEnabled`, `dataAccessMode`, `interactionModes`, `promptGraphDefinition`, `listedInStore` have no reader outside the VC folder; `knowledgeSpace` has no resolver and is always null. Test: `hosted-resources` pins that `listedInStore` plays no part. Spec: CM-52's model card prints a *fixed* data-access sheet, not `dataAccessMode`. Ruling: which of these are client-only switches to keep, which go to the engine, and which are dead?
4. **Knowledge-base profile update accepts a full profile but applies only the description (VCK-07).** Code: `UpdateKnowledgeBaseInput.profile` is an `UpdateProfileInput`; the service copies `description` only. Test/spec: none. Ruling: implement or narrow the input.
5. **Space-kind body-of-knowledge id is never validated (VCK-03).** Code: free string at create; register E5 counts 10 VCs whose id points nowhere and 159 orphan personas. Test: the read-back case only. Ruling: validate at create (existing space, same account?) and decide what a dangling VC should report.
6. **Conversion moves the callouts but not the kind (VCK-37).** Code: `bodyOfKnowledgeType` stays `alkemio-space` and `bodyOfKnowledgeID` keeps the (now emptied) space id after `convertVirtualContributorToUseKnowledgeBase`; the mutation description says "to be of type KNOWLEDGE_BASE". Test: a9 asserts the callout moved; `platform-roles-test-plan.md:205` already flags "the VC type label does NOT change — separate product finding". Ruling: set kind + id on success, or document the conversion as a content move.
7. **`rolesVirtualContributor` is ungated (VCK-39).** Code: returns any VC's credentials to any caller including anonymous. Mirrors CM finding 7 (`virtualContributor(ID)` ungated). Ruling: gate on READ of the VC, as `lookup.virtualContributor` does.
8. **Transfer VC returns the wrong GraphQL type.** Code/schema: `transferVirtualContributorToAccount` is declared `IInnovationPack` (`account.resolver.mutations.ts:569-571`, `schema.graphql:5320`) while resolving a VC. Test: a9 reads only `id`. Ruling: schema fix (breaking change report).
9. **Context ingest is requested but never used (VCK-14).** Code: every VC role grant publishes a context-purpose space ingest; the invocation path has the context check commented out and logs "still need to use the context". Spec: none. Ruling: drop the context ingest or wire it.
10. **Guidance ingest URLs are hard-coded (VCK-10).** Code: three production URLs in `ai.server.service.ts:288-292`, ignoring the VC's own body of knowledge and the environment. Ruling: configuration or product constant?
11. **No way to clear a well-known mapping (VCK-20).** Code: set-only; the a10 group refuses to run when CHAT_GUIDANCE had no mapping because it could not be restored. Ruling: add an unset, or accept.
12. **The subscription is the only live signal and it is on the retire list (VCK-12).** Code: `virtualContributorUpdated` fires only on the ready stamp; the rebuild drops subscriptions. Ruling: how the new client learns a VC became ready (poll `status`?).

## Gaps (no legacy case)

Untested rules by id: VCK-02, VCK-07, VCK-08, VCK-09, VCK-10, VCK-11, VCK-12, VCK-14, VCK-16, VCK-17, VCK-18, VCK-22, VCK-23, VCK-24, VCK-25, VCK-26, VCK-27, VCK-28, VCK-29, VCK-30, VCK-31, VCK-32, VCK-33, VCK-34, VCK-35, VCK-39; plus the untested clauses of VCK-01 (atomic create), VCK-13 (continue on failure), VCK-15 (omitted value), VCK-20 (audit row), VCK-21 (anonymous refused).

Behaviours the area has that neither reading nor tests pinned down:
- The end-to-end VC answer in a room (summon → engine → reply posted as the VC with sources) — W2 journey 9, parked while VCs are hidden in the client; no API-level case either (needs a live engine on the stack).
- What a VC does when its body-of-knowledge space is deleted (E5 dangling ids): refresh outcome, status, answers.
- Ingest of a knowledge-base-kind VC after its callouts change (is a re-ingest needed, and who triggers it — the `updateAiPersona` path has a "TBD: trigger a re-ingest?" comment).
- The ready stamp after a *second* ingest that fails for a reason other than vector insert (stays ready — VCK-11) — worth one case once the result queue can be driven.
- Deleting a VC that is bound to open threads: the interaction record stays on the room (nothing cleans `vcInteractionsByThread`); later messages in that thread try to invoke a deleted actor.
- A VC mentioned in a thread it was not started in (a later mention in an existing thread is ignored — VCK-28 path never parses mentions).
- The guidance conversation for a user registered while the mapping was absent (never recreated).
- Setting the well-known mapping to a VC id that does not exist (no existence check in `setMapping`).
- Configuration audit row for the well-known mapping and operations audit row for refresh-all.
- `virtualContributorUpdated` filtering (only the subscribed VC's events).

Someone who knows the engine must say which attributes are live.
2. **Which VC the CHAT_GUIDANCE mapping points at on acceptance/production today**, after the two repair migrations (`1773800000001`, `1773800000002`) — a live read of `platform.wellKnownVirtualContributors` and of a sample guidance conversation's members.
3. **Is the VC UI coming back?** VCs are hidden in the client since 2026-10-30 (journey 9 parked; the pinned guidance conversation hidden by client-web#10434 in v0.169.1). The rules above are API rules; whether any of them is user-reachable today is a product question, not a rule.
4. **Does spec 007 ("knowledge base search") intend to cover VC knowledge bases?** The spec scopes search by innovation-flow state, which a VC knowledge base does not have; the catalogue row AI-1 lists "search" under the knowledge base. Confirm the catalogue wording.
5. **Which deployed queue bindings exist for the ingest/result queues on each environment** (`alkemio.yml` names are env-overridable); without them VCK-09/11 cannot be exercised on the test stack.
6. **Whether `hosted-resources`' "listedInStore plays no part" is the intended product rule** or a missing store feature (F-3).
7. **Is the VC refresh (VCK-09) reachable by the client at all?** `refreshVirtualContributorBodyOfKnowledge` is unreached by any lib function (catalogue AI-1 "unreached"); if the client never calls it, the only ingest trigger is creation-time (not found in the server — nothing publishes an ingest on create) or the POA refresh-all. Someone must confirm how a new VC gets its first ingest.
