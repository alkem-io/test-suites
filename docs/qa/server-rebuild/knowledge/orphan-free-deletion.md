# Orphan-free deletion — behaviour knowledge

_Extracted 2026-11-06 from three sources: server develop @ `eeecf9ddb` (Release/79) code + `schema.graphql`; the legacy server-api suite (`server-api/src/functional-api/orphan-free-deletion/`, 3 files, 12 cases, plus `_support/owned-records.ts`); the specs, issues and docs listed in § Sources. Scope: what deleting a user, an organisation, a space, an account or one of their owned records removes, reassigns or refuses — profile, storage, authorization policies, roles and credentials, rooms, sign-in identity, sessions, audit — and where orphans are known to be left. Who may delete a space, callout or template is the journey / callout / templates area; who may delete a user or organisation is stated here because the two paths carry their own gates. WHAT and WHY only — no mutations, fixtures or request params. Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". Evidence paths are relative to the server repo unless prefixed `test ›` or `spec ›`._

_Review load: 9 findings · 2 unknown-why rows · 3 untested rows (9 ids under Gaps once untested clauses are counted) · 21 constants to tick · 5 open questions. Manual points sit in five places: the Findings, the `unknown-why` rows, the `untested` rows (repeated under Gaps), the "product must rule?" column of the constants, and the Open questions._

## Where this lands in the new core

The new core stores no authorization policies, no derived credentials and no per-entity licence snapshot, so DEL-15, DEL-21 and the whole G1 class vanish by construction (register class **V**): there is no policy row to orphan, and "every remaining policy is reachable from a live record" stops being a property anyone has to prove. What remains are the real ownership cascades — actor → profile/storage/settings/credentials, space → about/collaboration/community/licence, account → resources — which should be declared as foreign keys with `ON DELETE` behaviour (catalogue: one actor table, resources keyed by `account_id`) instead of ordered service code, so that DEL-04/09/12/14 become single transactional deletes and DEL-13 (#6648) cannot recur. Three things the ETL must carry: (1) the W4 register's **Q** rule — orphan policies, buckets, files, Matrix rooms and accounts (G1, F6, P1, P4) are reported, never dropped silently, and the counts go on the expected-loss list; (2) the sentinel (DEL-06) becomes a nullable author reference rendered as "former member", not a magic id; (3) the external legs — file bytes, Kratos identity, sessions, and the Matrix deprovisioning that DEL-08 says is still missing — stay post-commit, idempotent and audited (DEL-07), because they are not in the database at all. Error texts are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **Deleting an actor leaves its chat identity (DEL-08).** Code: no Matrix call on the user, organisation or VC deletion path; room membership is only dropped on explicit role removal. Spec 054: out of scope for v1, "sibling story filed immediately after v1". Data: W4 P4 — 84 orphan Matrix accounts, 65 still joined, 1,780 messages by deleted senders; filed server#6728. Ruling: confirm the sibling story exists and is scheduled; until then the help page must keep saying the chat identity persists (054 FR-024).
2. **A room row is deleted before the chat server confirms (DEL-16).** Code: `deleteRoom` removes the row, then calls the adapter, which returns `false` on failure, which nobody reads. Spec 082 FR-008: adapter failures log, never block. Data: W4 P1 — 427 orphan Matrix rooms; filed server#6727. Ruling: record the failed Matrix delete (outbox/audit) so an operator can finish it, or accept the leak.
3. **Organisation, space and VC deletions are not atomic (DEL-09/12/18).** Code: the organisation path runs with no transaction; `deleteSpaceOrFail` runs step by step; the VC and organisation-account wrappers open a transaction whose manager the steps ignore — 054 "Assumptions" says the same of the old user path ("the wrapper propagates nothing and is not actually transactional"), which the saga fixed for users only. Test: none forces a mid-way failure outside the user saga. Ruling: accept retryable partial deletes (the space path is designed to be retryable) or extend the saga pattern.
4. **Half-created spaces cannot be deleted (DEL-13).** Code: the delete loads collaboration/community/about/storage/licence and throws `RelationshipNotFoundException` when any is missing — the same anomaly the reset learned to skip (DEL-21). Issue server#6648 (14 live on ACC). Test: none. Ruling: a tolerant delete for broken spaces, or an ops-only repair path.
5. **Orphans are skipped, never swept (DEL-21).** Code: the only sweep ever run targeted 'agent'-typed rows; `resilientCascade` skips a broken subtree and leaves its stale rules (crosscheck F2). Data: G1 ~9,400 orphans, inert while nobody holds retired credentials. Spec: #6655 cleanup migration deferred. Ruling: run #6655 before the dry-run baseline, or classify G1 as V and stop.
6. **The orphan oracle is an existence oracle for everyone.** Code: `lookup.authorizationPolicy` loads the row before checking `PLATFORM_OPERATIONS_ADMIN`, so a non-POA caller gets `ENTITY_NOT_FOUND` for a missing id and `FORBIDDEN` for a real one; `lookup.license(ID)` has no privilege check at all. Test plan § Security lists both as open questions to the reviewer. Ruling: route as a security finding (attach to the server#6663 "leaks through error shape" family rather than a new issue, per the register convention).
7. **Three owned policies cannot be observed (DEL-15).** `Template.callout.framing.authorization`, `CommunityGuidelines.profile.authorization` and `framing.poll.authorization` resolve null, so GA-2/GA-4/GA-5 cannot assert them (GA-2 reads the poll policy from another answer). Reported on server#6614; resolver gap, not a known leak. Ruling: fix the resolvers, then extend the cases.
8. **Failed creates can leave owner-less policies.** Only the callout create path rolls its children back (#6679); other create paths are unfixed (test-plan D-3). Test: none possible over the API (rolled-back children return no id). Ruling: unit-level only, or an ops SQL probe (W4 register class V).
9. **The space-deletion refusal text embeds the id; the organisation refusal has a grammar slip.** `Unable to remove Space (<id>) …` contradicts the repo rule against dynamic data in exception messages; "account contain one or more resources". Rebaseline rows when cleaned; not behaviour changes.
