## Where this lands in the new core

The catalogue puts CT-4 in slice 4–5 as a `document` of engine `yjs` with a `share_link` for guests (`catalogue/README.md:79`); the briefing drops stored authorization policies, every reset mutation and the matrix-adapter, and uploads files straight to the file container (`plan.md` § 1). Every rule above survives as a behaviour; what changes is the mechanism. (1) The content policy (WBD-09/10) becomes a rule evaluated at read time, so the "recomputed at the next reset" clauses — and Findings 1 and 2 — disappear by construction; the new core must still decide whether PCFA may edit a "contributors" board (today it cannot). (2) Guest access (WBD-19..22) becomes a `share_link` row: the privacy question of Finding 4 (a link on a board in a private space) must be answered before that row is modelled, and the "any signed-in user" grant should become explicit. (3) Drafts (WBD-24..27) become a document with an expiry attribute; the per-draft serialization and the "mark consumed before deleting" order are invariants to keep, the advisory locks are implementation. (4) The room contract (WBD-13/14: room-owned version, pointer, server-as-collaborator) belongs to the engine, not the core; the `migrated` flag and WBD-35 vanish at cutover. (5) Previews (WBD-28) are client-generated today — the core should say whether a preview is a stored visual or a rendered view. Error texts are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **Spec 023's rollback, metrics and audit are not implemented (WBD-22).** Code: `appendSettingsDrivenCredentialRules` writes `verbose`/`debug` log lines only; there is no transaction around the cascade, no revert of `allowGuestContributions` on failure (FR-009), no metrics (FR-011), no audit row with triggering user/action (FR-012/013); a failure to resolve admin credentials silently yields no admin rule. Test: none. Ruling: drop those requirements from the spec, or file the gap.
2. **"Immediately" is "at the next recompute" (WBD-21/22).** Spec 021 (edge case) and 023 FR-005/FR-008 promise synchronous revocation when the space setting flips off. Code: the guest rule and public-share rights are only re-derived inside `applyAuthorizationPolicy` for the board; whether the space-settings mutation cascades that recompute over every callout and board was not read (Open question 1). Test: none. Ruling: verify live; if the cascade exists, record the latency; if not, file.
3. **Workspace spec 006 describes a mechanism the code no longer uses (WBD-14).** Spec: server emits a versioned delta on a dedicated RabbitMQ queue, the (archived) whiteboard-collaboration-service merges it and broadcasts `SCENE_UPDATE`. Code: the server joins the room through `CollaborationDocumentService` as a Yjs collaborator and never writes the snapshot or pointer directly; the queue constant remains in `providers.ts:16-17`. Ruling: mark 006 superseded (and say by what — the excalidraw-yjs/collaboration-service contract is not in any spec on this checkout), and check whether the queue is still declared anywhere.
4. **A guest-enabled board ignores the space's privacy (WBD-20).** Code: the `public-access` rule is appended to the board's own policy with cascade for `GLOBAL_GUEST` and `GLOBAL_REGISTERED`, so with the space setting on and the toggle on, a board inside a **private** space is readable and editable by any named visitor and any signed-in user; the toggle gate is the space setting, not privacy. Spec 021 FR-002 states exactly this for "guests and any authenticated user"; spec 022 only promises a "secure posture" by default and never defines a guest. Test: none; the matrix models `pub-open+guests` only. Ruling: is a guest link on a private-space board intended? Should the link be read-only, or edit as today?
5. **Direct board edits and deletions by a platform role are not audited (WBD-29).** Code: `updateWhiteboard` / `deleteWhiteboard` resolvers have no platform-audit call, while the contribution deletion path audits PCFA (CAL-32) and the server CLAUDE.md requires a row for any platform-role action. Ruling: file (audit gap) or record as accepted.
6. **A new identifier on a board update is silently ignored (WBD-12).** Code: `UpdateWhiteboardInput.nameID` is documented as changing the URL, but `updateWhiteboard` never copies it. Test: none. Ruling: implement or remove the field.
7. **Preview "auto/custom/fixed" is a client instruction the server does not enforce (WBD-28).** Code: the server stores the mode and whatever `whiteboardPreview` visual the client uploads. Issue: client-web#10283 — a callout-template whiteboard framing never gets a preview image while a standalone template does. Ruling: product decides whether the preview is a server guarantee; the client defect is filed.
8. **The activity-log proof for whiteboards is switched off.** Test: `WHITEBOARD_CREATED` is asserted only inside a `test.skip` in all three activity-log files ("To be updated with the changes related to whiteboard callouts"). Code: the activity entry is written (`callout.resolver.mutations.ts:957-968`). Ruling: re-enable or rewrite the case; until then WBD-34's activity half is a code reading.

## Open questions (could not be determined from the three sources)

Read-only extraction against the code, the tests and the specs; nothing below could be settled without a live stack or a source outside the three. Each needs a person to answer it or route it.

1. **Does changing `allowGuestContributions` cascade a rights recompute down to every board?** The space-settings mutation path is outside this area and was not read; Finding 2 depends on it.
2. **What the collaboration service does with `isMultiUser`, `authorizationPolicyId` and a revoked guest.** Read-only vs write admission, the single-editor rule, `MaxConnsPerRoom`, and the "not found" spec 021 promises for a revoked guest all live in the Go collaboration service and excalidraw-yjs (server pins 0.5.5); the old whiteboard-collaboration-service and collaborative-document-service repos were archived 2026-10-01 and nothing in this workspace documents the successor's contract.
3. **Is the 006 queue still consumed anywhere?** `WHITEBOARD_COLLABORATION_SERVICE` (`providers.ts:16-17`) survives; whether a consumer or a RabbitMQ declaration still exists was not checked.
4. **Where is the W2 whiteboard walk?** PR test-suites#702 (excalidraw-yjs#13 QA) lives on another worktree; on this checkout `grep -ril excalidraw` finds only the template-form helpers. Until a walk draws and reads back content, every editing rule here is a code reading.
5. **"WhiteboardRt" in the storage suite.** Three `Access to WhiteboardRt Callout …` blocks name a real-time whiteboard kind that no longer exists in the code; the crosscheck notes they duplicate the whiteboard-framed blocks. Retire or rename.
6. **Where is the board size cap?** The server has none (the MCP 262,144-byte request limit is the only number); W4 M4 found 2 boards above 1 MB and 173 empty ones. The cap, if any, is in the collaboration service.
7. **The client-side preview and `isMultiUser` footers.** client-web#10283 (no preview on callout-template framings) and the whiteboard "one editor at a time" footer are client behaviour over server facts; nobody has checked that the footer appears exactly when `isMultiUser` is false.
