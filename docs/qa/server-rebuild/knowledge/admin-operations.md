## Where this lands in the new core

The rebuild briefing (plan § 1) removes stored authorization policies and "every reset mutation": authorization is computed at read time from credentials, so OPS-01…OPS-13 and OPS-36 are **dead-by-design** — there is nothing to reset, no worker, no version coupling, no orphan policies (register G1 and crosscheck F2/F3 become ETL concerns, not runtime ones). What survives as behaviour: the ops seat and its bounded family (OPS-10/OPS-20, "ops namespace" in the catalogue), the audit trail (OPS-40–48 — the catalogue keeps a role-attributed, append-only record; the new core should decide whether operations rows keep a coarse tier, F-4), the background jobs (drafts, signing, push, digest — OPS-30–34, each belonging to its own area's slice) and the admin console reads (OPS-50, MB-8). Three facts found here should shape the model: (1) the task queries and the internal REST surface are unauthenticated today (OPS-18, OPS-22) — the new surface must gate job status and give scheduled jobs an identity that the audit trail can name; (2) search ingest, prune and geolocation are the only operations whose *effect* matters once resets are gone, and none has an effect-level case (gaps); (3) the audit reader has no screen and cannot reach organisation-subject rows (F-11), so the audit read surface is a design input, not a port.

## Findings (sources disagree, or likely defect)

1. **The reset worker's build is unchecked (OPS-12).** Code: the worker is the same image and applies whatever rules it was built with; no version or schema check. Test: `destructive-positives` skips the reset-all positive for this reason; the client checklist records the 2026-09-21 incident (worker image from 2026-08-10 rewrote every policy with pre-027 rules). Spec: 032 says a reset "must not alter the role's own grant set" (idempotent) — true only when the images match. Infra: two separate pins with a comment. Ruling: add a guard (worker refuses or warns when its version differs from the API's, or the publisher stamps the expected version into each message), or make the deploy coupling mechanical; until then record it as an operations rule.
2. **A skipped subtree is a silent success (OPS-05).** Code: `resilientCascade` logs and returns `[]`; the task records the entity as finished. Test: none. Data: crosscheck F2 (retired-credential rules on 1,018 files, 872 buckets, 2,000 tagsets … under fresh parents) and F3 (empty-rule policies that deny everyone) are exactly this pattern on ACC. Ruling: the task should report skipped steps (or the row should be repaired), and the register should split "orphan" from "live but skipped".
3. **Orphan policies have no sweep (OPS-36).** Code: reset-all walks live records only (#6614); nothing scheduled touches `authorization_policy`. Test: the orphan plan says the "every remaining policy is reachable" property "has no covering test and cannot have one here". Data: G1 ~9,400 orphan rows; #6614 counted 13,928 retired-credential policies on an ACC copy; #6657/#6655 is a one-off reversible migration. Ruling: one-off only (accepted until the new core) or a recurring sweep?
4. **Operations rows always say `platform_admin` (OPS-41).** Code: `platform.operations.audit.service.ts:96` writes the coarse tier for every operations row, "by design". Test: none asserts an operations row's initiator role. Ruling: attribute operations rows through `resolveInitiatorRole` like the other families, or amend FR-025 to name the operations family as a permanent carve-out.
5. **Task queries are open to everyone (OPS-18).** Code: `task` and `tasks` declare no privilege; the guard admits anonymous. Result lines name account/organisation/user ids. Behaviours the area has that neither reading nor tests pinned down:
- The effect of any reset on a stored policy — that a rule introduced by a new build appears on an existing entity only after its reset, and that the policy of an untouched entity is byte-identical after a second reset (S-06 covers one organisation's two Support rules only).
- Worker retry and dead-letter: a reset that fails five times is dropped and the task shows the error; a reset that fails once is retried and succeeds.
- Drain: a rollout during a reset loses no message.
- Task settling: a counted task reaches COMPLETED exactly when the last item lands; duplicate delivery does not over-count; an expired task is a clean failure for pollers.
- Prune: a notification older than the retention is gone and a newer one stays; the 101st notification of a user is removed oldest-first; read state is ignored; an invalid setting deletes nothing.
- Search ingest: the alias points at the new indices and the old ones are deleted; a failure leaves the previous index serving.
- Geolocation: a location with a country and no coordinates gets them; one bad location aborts the rest.
- Avatar migration: an external avatar becomes a document in the profile bucket; an unreachable one is left alone.
- The four sweeps (drafts, signing attempts, push subscriptions, digests) firing at all, and never firing on the worker.
- Operations audit rows: one per execution, success and failure, subject NULL for platform-wide, actor named, error text capped.
- Boot-time platform reset on an empty policy.
- The REST routes: reachable in-cluster, unreachable publicly, task 404 after expiry.
- Any operation (ingest, prune, avatars, geolocation, collection cleanup, BoK refresh) on an acceptance-size dataset — duration, and for `resetLicenseOnAccounts` whether one request survives it.
