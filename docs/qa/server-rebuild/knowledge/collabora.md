# Collabora — office documents — behaviour knowledge

_Extracted 2026-11-06 from three sources: server develop @ `eeecf9ddb` (Release/79) code + `schema.graphql`; the legacy server-api suite (`server-api/src/functional-api/collabora/`, 2 files, 23 cases = 23 test blocks, 0 skipped); the specs, issues and docs listed in § Sources. Scope: the office document (Collabora/WOPI) as a callout framing or a callout contribution — its kinds, the three ways it is created, opening in the editor, who may edit, rename, replace and delete it, its preview, and the records it writes. The office-documents licence flag (ENT-32), the callout rules for framings and contributions (CAL-08, CAL-26..30, CAL-70, CAL-73) and the storage access cells (matrix `document`, crosscheck F1/F11) are cross-referenced, not re-derived. WHAT and WHY only — no mutations, fixtures or request params. Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". Evidence paths are relative to the server repo unless prefixed `test ›` or `spec ›`. The extraction notes with every file:line are in `collabora-dossier.md`._

_Review load: 9 findings · 1 unknown-why row · 8 untested rows (gaps) · 25 constants to tick · 7 open questions. ## Where this lands in the new core

The office document becomes a `post` kind whose content is a blob in the file container; the catalogue (CT-6) retires the separate `wopi` store — locks and document versions migrate or reset, and WOPI moves into the file container. Every rule above stays a behaviour; what changes is the plumbing. Three facts found here should shape the model: (1) today the document's own policy is **mirrored onto the backing file** so an external editor can authorize per request (OFD-14, `authorization.util.ts`) and the replace flow has to re-mirror it by hand — in the new core the file container should authorize against the post directly, with one read right and one content-write right (`contribute` → `update-content`), and the creator rule should be an ordinary ownership fact on the post; (2) the identity of a document is the **post**, not the file: replace re-points a file reference while id, creator, rights and title stay (OFD-17), and a rename is a dual-store write today (OFD-15) — a single store removes the rollback dance and makes the file name derivable (`title + extension from the stored format`); (3) the three creation modes collapse to "blob from upload / blob copied from another post / empty blob of a format", and the licence gate (OFD-09) is a read-time check on the owning space's plan at introduction only — keep that boundary (existing documents stay when the plan lapses) and decide explicitly whether knowledge bases and templates are inside it (F-6). The analytics boundary — fire-and-forget domain events after the primary work, window aggregates keyed by stable file id — is worth keeping verbatim; the save-path health check and the lock-aware replace are contracts the editor already relies on. Error texts are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **Replace title: spec 014 says never persist, spec 016 and the code persist (OFD-15/17).** Code: `resolver.mutations.ts:130-154` applies the optional title through the rename path. Test: `swaps the backing file and applies the new display name` pins the persisted title. Spec: 014 FR-009/FR-015 "this feature does not persist it" vs 016 FR-009 "the optional title … MUST be persisted". Ruling: mark 014 FR-009/FR-015 superseded by 016 (documentation only).
2. **Replace allowlist text is stale (OFD-03).** Spec 014 FR-004 names `.docx .xlsx .pptx`; code accepts 13 formats (036 added PDF; doc/odt/rtf/xls/ods/csv/ppt/odp/odg were there from #5970); the legacy case replaces with `.odt`. Ruling: product confirms the 13-format list is the intended surface (the client's own import list may be narrower — client-web#10423 thread mentions "13 MIMEs are accepted"), then rebaseline 014.
3. **Replace on contribution documents (OFD-17).** Spec 014 FR-011: offered only on framing documents, "contributions do not exist yet". Code is surface-agnostic (`service.ts:547-553`) and the legacy case `refuses a replacement that is not an allowed OfficeDocs format` replaces a **contribution** document. Ruling: record "replace applies to any document" as the rule; the client surface is the only remaining restriction.
4. **Stale code comment: inline document contributions "never appear in a bulk" (OFD-07).** `callout.service.ts:503-505` says document contributions are created only through import; `callout.contribution.service.ts:238-245` creates them inline and the legacy fixture does exactly that (`createCollaboraContributionCallout`). Ruling: fix the comment; the inline path is a supported behaviour (it is how the callout-with-contributions create works).
5. **Rename validation lives only in the client (OFD-15).** Spec 016 FR-007: non-blank, min 3, max `SMALL_TEXT_LENGTH`. Code: `UpdateCollaboraDocumentInput.displayName` is `@IsOptional() @IsString()`; the resolver treats `''`/absent as a no-op and persists any other string (one character, 10,000 characters) into the profile and the file name; the in-editor path ignores blank only. Test: none. Ruling: server-side validation to add, or accept the client as the gate (then the API contract differs from the UI).
6. **Knowledge bases and template sets are outside the licence (OFD-09).** Code: `ensureOfficeDocsAllowedForCalloutsSet` returns when the set has no collaboration. Test: `opens normally even though attribution cannot resolve a Space` creates an office document on a VC's knowledge base **without any plan**; the template suite entitles both spaces (so it proves nothing here). Spec 002 scopes the gate to Collaborations (Assumptions) and ENT-32/CAL-08 say "for every role … fail closed"; client-web#10423 leaves "templates in spaces without the entitlement" undecided (#9827). Ruling: is a VC owner without a plan meant to create office documents in a knowledge base, and is a template document free to create (its apply is gated by the target)?
7. **A former member keeps replace and delete but loses edit (who-may).** Matrix row `creator-former-member`: create/update/delete C via the creator self-management rule, no contribute → no update-content. So the person who uploaded a document can, after leaving the space, still swap its file for another one or delete it, yet cannot open it for editing. Code: `collabora.document.service.authorization.ts:566-584`. Test: none. Ruling: keep the creator rule (consistent with posts/whiteboards — CAL-29) or drop it on membership loss.
8. **Missing lock endpoint ⇒ replace proceeds (OFD-17).** Code treats HTTP 404 from the lock-status route as "unlocked" and logs at error; spec 016 FR-013 asks exactly that ("a missing lock-status endpoint MUST NOT permanently block replace"), spec 014 FR-013 says "the swap proceeds only when no active session exists". Deliberate, but it means a wrongly routed save service silently disables the active-edit guard. Ruling: accept (document as a deployment precondition) or fail closed on 404 too.
9. **A rename failure after a successful replace reports success with the old title (OFD-17).** Code: `resolver.mutations.ts:138-154` — the swap is not idempotent, so the rename error is logged and the mutation returns the swapped document under its previous name. Test: none (the happy path only). Spec: none. Ruling: surface a warning in the response or accept "user renames again".
