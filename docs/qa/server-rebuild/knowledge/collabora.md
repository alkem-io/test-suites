# Collabora (office documents): behaviour rules

_What the platform does today for office documents edited with Collabora, as the main content of a callout or as a contribution: the kinds, the three ways a document is created, opening it in the editor, who may edit, rename, replace and delete it, its preview, and the records it writes. The office-documents licence (ENT-32) and the callout rules are in `entitlements.md` and `callout.md` and are only cross-referenced here. What it does, why, who may, and what is still to answer. The file has three sections: **1. Rules**, **2. Rights**, **3. Open questions**, with the evidence in an **Appendix**._

_Open questions per owner: Product Lead 0 · Technical Lead 6 · Quality Lead 6 · Service Operations Lead 1. By state: 9 open · 4 with a suggested answer · 6 decided. Proof of the 23 rules: 14 proven by a test · 9 untested (Appendix A)._

_Whys of the 23 rules: 23 rest on a source or a product decision · 0 carry a draft · 0 have none._

**How to read it**

- **Rule** is one or two plain sentences. The exact behaviour, with error messages and limits, is in Appendix A under the same id. The new core is checked against the exact text.
- **Why: business** is what Alkemio needs. **Why: product** is the user story. **Why: technical** is the engineering reason. A rule needs at least one why, and gets a second or third only where it adds something for the decision or the code. "—" means none is given.
- A why that names a spec, issue, pull request, code comment or code line rests on that source. A why, or the part of a why, ending in _(draft)_ was written by QA and no source states it: product keeps, rewrites or deletes it, and sets **Decided by**. A user story always ends in its "so that"; where no source gives one, QA wrote it. A rule with no why at all carries an open question in section 3.
- **Decided by** names the source of the decision: a spec, a commit or pull request, an issue or a document. "Not decided: exists in the code" means the behaviour is in the code and nobody chose it. "Not decided: a defect" means the behaviour is a fault.
- A marker in bold at the end of a rule points at section 3: **(open: F3)** means a question on this rule is still open, **(defect: F2)** means today's behaviour is a fault and must not be copied as intended, **(defect in part: F5)** means part of it is. A rule with no marker stands as written. Every rule is logged as the server behaves today, also when that is not the intended end state. Whether a test proves the rule sits in Appendix A as **proven** or **untested**.
- Hard rules are not marked yet. Some rules are choices that a new feature may challenge, and some can never change; a later version will mark the second kind with "(hard rule)" after the why that makes it so. Until then, no marker does not mean a rule is open to change.

### C. Findings and questions in full

_The original text of every finding (F) and open question (OQ), with its evidence and its ask. Inside these texts the old spelling "F-3" means F3._

#### Findings

- **F1 — Replace title: spec 014 says never persist, spec 016 and the code persist (OFD-15/17).** Code: `resolver.mutations.ts:130-154` applies the optional title through the rename path. Test: `swaps the backing file and applies the new display name` pins the persisted title. Spec: 014 FR-009/FR-015 "this feature does not persist it" vs 016 FR-009 "the optional title … MUST be persisted". Ruling: mark 014 FR-009/FR-015 superseded by 016 (documentation only).
- **F2 — Replace allowlist text is stale (OFD-03).** Spec 014 FR-004 names `.docx .xlsx .pptx`; code accepts 13 formats (036 added PDF; doc/odt/rtf/xls/ods/csv/ppt/odp/odg were there from #5970); the legacy case replaces with `.odt`. Ruling: product confirms the 13-format list is the intended surface (the client's own import list may be narrower — client-web#10423 thread mentions "13 MIMEs are accepted"), then rebaseline 014. **Product, 2026-11-20:** the 13 formats are intended; amend spec 014.
- **F3 — Replace on contribution documents (OFD-17).** Spec 014 FR-011: offered only on framing documents, "contributions do not exist yet". Code is surface-agnostic (`service.ts:547-553`) and the legacy case `refuses a replacement that is not an allowed OfficeDocs format` replaces a **contribution** document. Ruling: record "replace applies to any document" as the rule; the client surface is the only remaining restriction. **Product, 2026-11-20:** replace applies to any document; amend spec 014.
- **F4 — Stale code comment: inline document contributions "never appear in a bulk" (OFD-07).** `callout.service.ts:503-505` says document contributions are created only through import; `callout.contribution.service.ts:238-245` creates them inline and the legacy fixture does exactly that (`createCollaboraContributionCallout`). Ruling: fix the comment; the inline path is a supported behaviour (it is how the callout-with-contributions create works).
- **F5 — Rename validation lives only in the client (OFD-15).** Spec 016 FR-007: non-blank, min 3, max `SMALL_TEXT_LENGTH`. Code: `UpdateCollaboraDocumentInput.displayName` is `@IsOptional() @IsString()`; the resolver treats `''`/absent as a no-op and persists any other string (one character, 10,000 characters) into the profile and the file name; the in-editor path ignores blank only. Test: none. Ruling: server-side validation to add, or accept the client as the gate (then the API contract differs from the UI).
- **F6 — Knowledge bases and template sets are outside the licence (OFD-09).** Code: `ensureOfficeDocsAllowedForCalloutsSet` returns when the set has no collaboration. Test: `opens normally even though attribution cannot resolve a Space` creates an office document on a VC's knowledge base **without any plan**; the template suite entitles both spaces (so it proves nothing here). Spec 002 scopes the gate to Collaborations (Assumptions) and ENT-32/CAL-08 say "for every role … fail closed"; client-web#10423 leaves "templates in spaces without the entitlement" undecided (#9827). Ruling: is a VC owner without a plan meant to create office documents in a knowledge base, and is a template document free to create (its apply is gated by the target)? **Product, 2026-11-20:** stays as today, no wish; listed as a check on the product issues list.
- **F7 — A former member keeps replace and delete but loses edit (who-may).** Matrix row `creator-former-member`: create/update/delete C via the creator self-management rule, no contribute → no update-content. So the person who uploaded a document can, after leaving the space, still swap its file for another one or delete it, yet cannot open it for editing. Code: `collabora.document.service.authorization.ts:566-584`. Test: none. Ruling: keep the creator rule (consistent with posts/whiteboards — CAL-29) or drop it on membership loss. **Product, 2026-11-20:** stays as today; ending the creator's rights on leaving is a wish on the product issues list.
- **F8 — Missing lock endpoint ⇒ replace proceeds (OFD-17).** Code treats HTTP 404 from the lock-status route as "unlocked" and logs at error; spec 016 FR-013 asks exactly that ("a missing lock-status endpoint MUST NOT permanently block replace"), spec 014 FR-013 says "the swap proceeds only when no active session exists". Deliberate, but it means a wrongly routed save service silently disables the active-edit guard. Ruling: accept (document as a deployment precondition) or fail closed on 404 too.
- **F9 — A rename failure after a successful replace reports success with the old title (OFD-17).** Code: `resolver.mutations.ts:138-154` — the swap is not idempotent, so the rename error is logged and the mutation returns the swapped document under its previous name. Test: none (the happy path only). Spec: none. Ruling: surface a warning in the response or accept "user renames again". **Product, 2026-11-20:** stays as today; a warning is a wish on the product issues list.

#### Open questions

- **OQ1 — The save service is unread.** `wopi-service` is not a workspace repo (`repos.yaml` has no entry), so token TTL, lock expiry, the preview endpoint's authorization, window flushing and the guest/anonymous exclusion of 003 FR-002/003 are known only from specs 003/015/059 and the server adapter. Someone with the repo should confirm OFD-19/OFD-21 against its code.
- **OQ2 — Analytics records cannot be seen through the API.** The opened/replaced/uploaded records, the contribution/view windows, the `actorType` partition and the `alkemio` flag are Elasticsearch-only (README "What this suite cannot prove"; `scripts/verify-collabora-lookup-records.mjs` reads the server log, which needs `LOGGING_FORMAT_JSON=true`). Decide whether W2/W4 verify them from Kibana or leave them unverified.

### F. Where this lands in the new core

The office document becomes a `post` kind whose content is a blob in the file container; the catalogue (CT-6) retires the separate `wopi` store — locks and document versions migrate or reset, and WOPI moves into the file container. Every rule above stays a behaviour; what changes is the plumbing. Three facts found here should shape the model: (1) today the document's own policy is **mirrored onto the backing file** so an external editor can authorize per request (OFD-14, `authorization.util.ts`) and the replace flow has to re-mirror it by hand — in the new core the file container should authorize against the post directly, with one read right and one content-write right (`contribute` → `update-content`), and the creator rule should be an ordinary ownership fact on the post; (2) the identity of a document is the **post**, not the file: replace re-points a file reference while id, creator, rights and title stay (OFD-17), and a rename is a dual-store write today (OFD-15) — a single store removes the rollback dance and makes the file name derivable (`title + extension from the stored format`); (3) the three creation modes collapse to "blob from upload / blob copied from another post / empty blob of a format", and the licence gate (OFD-09) is a read-time check on the owning space's plan at introduction only — keep that boundary (existing documents stay when the plan lapses) and decide explicitly whether knowledge bases and templates are inside it (F-6). The analytics boundary — fire-and-forget domain events after the primary work, window aggregates keyed by stable file id — is worth keeping verbatim; the save-path health check and the lock-aware replace are contracts the editor already relies on. Error texts are rebaseline rows, not rules.
