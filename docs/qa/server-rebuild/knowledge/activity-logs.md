_Extracted 2026-11-06 from three sources: server develop @ `eeecf9ddb` (Release/79) code + `schema.graphql`; the legacy server-api suite (`server-api/src/functional-api/activity-logs/`, 5 files, 55 cases, 3 skipped); the specs, issues and docs listed in § Sources. Scope: which actions write an activity entry and what it carries, the per-collaboration log, the two platform feeds (paginated and grouped), the "my spaces" / membership ordering that the same rows drive, and what happens to entries on transfers, moves and deletions. Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". Evidence paths are relative to the server repo unless prefixed `test ›` or `spec ›`._

## Who may (role × action)

## Where this lands in the new core

The catalogue's CT-12 row ("Activity log and activity feed") says: append-only activity, partitioned; counts at read; `activityCreated` unreached; API coverage full, the UI feed absent from the nightly; grouping semantics are a named rebaseline candidate. Every rule above stays valid as a behaviour (what writes an entry, who may read it, scope of the feeds, what moves with a callout) and only the storage changes: the twelve entry kinds become one typed row keyed by the recursive `post` document (callout / contribution / comment collapse into post kinds, so ACT-03/06/07 become one rule with a kind), membership entries hang off the credential on the space, and the per-collaboration log becomes a query on the space document with the SQL authorization verdict deciding visibility — which closes F-4 (child flag) and F-7 (hidden rows) for free if visibility is a column the verdict reads. Four facts found here should shape the model: (1) the row has no foreign keys and ~8,100 dangling rows on ACC (ACT-17, W4 F8) — the new core must decide between cascading deletes and tombstones at write time, not drop at read time (ACT-26/61); (2) the grouped feed's actor × subject × type collapse (ACT-57) and the uncapped limits (ACT-62) are the rebaseline; (3) only user actors are recorded (ACT-14) — the actor model of the new core makes a VC author a first-class actor, so product must say whether VC activity appears; (4) the dead `CALLOUT_WHITEBOARD_CONTENT_MODIFIED` kind (ACT-12) and the missing office-document kind (ACT-04) go to the expected-loss / rebaseline list. The live push (SUB-10) is dropped with the rest of the subscriptions.

## Findings (sources disagree, or likely defect)

1. **Office-document contributions write no activity (ACT-04).** Code: `processActivityCollaboraDocumentCreated` only reports to Elasticsearch; no adapter method, no entry type. Test: none. Spec/knowledge: callout table CAL-30 lists "document created" among the typed entries; `docs/how-to-add-activity.md` expects every contribution kind in log, feed and grouped. Ruling: add the entry kind, or correct CAL-30 and accept that documents are invisible in the timeline.
2. **Calendar entry text loses its first character (ACT-09).** Code: `profile.description?.substring(1, 100)` (`activity.adapter.ts:202-204`). Test/spec: none. Ruling: defect (should be `substring(0, 100)`); rebaseline the text shape when fixed.
3. **"Whiteboard content modified" is a dead kind (ACT-12).** Code: no producer since `1650462ec` (#4973); enum, schema, builder and the client's exclusion filter remain. Test: the AF cases send the exclusion. Spec 024 `:37` still names it. Ruling: retire the kind (expected-loss list) or restore a producer from the collaboration service.
4. **A top-level space's own entries come back as children (ACT-25).** Code: the L0 branch of `getChildCollaborationsOrFail` selects every space whose `levelZeroSpaceID` is the L0 — the L0 itself included (`space.service.ts:279-281`) — and `activityLog` flags any entry whose collaboration is in that list; the feed path dedups (`activity.feed.service.ts:321-324`), the log path does not. Test: no case uses `includeChild`. Ruling: defect; the client's "happened in a subspace" rendering is wrong for the parent's own entries.
5. **Grouped feed ignores `excludeTypes` (ACT-58).** Code: the grouped input inherits the field; the service never passes it. Test: AF-14 sends it (via `baseArgs`) and asserts nothing about it. Ruling: implement or remove from the grouped input.
6. **Uncapped feed sizes (ACT-62).** Code: grouped `limit` runs raw on the first query; `first` has no maximum. Test plan: pre-existing, "no ticket found". Ruling: cap (and make it a rebaseline constant) — the 100-row cap already exists for the refetch loop.
7. **Hidden entries still drive "my spaces" and membership ordering (ACT-72).** Code: `getMySpacesActivity` and `getLatestActivitiesPerSpaceMembership` have no `visibility` predicate; the log, both feeds and the MCP tool filter it. Test/spec: none. Ruling: one visibility rule for every reader.
8. **Post comments vs callout comments differ on draft callouts (ACT-06/07).** Code: a comment on a post is recorded whatever the callout's visibility; a comment in the callout's own discussion only when published and on a space. Test/spec: none. Ruling: one rule ("comments count only on published callouts") or document the asymmetry.
9. **Non-user actors (ACT-14, ACT-10).** Code: VC and organisation comments/updates are skipped (FIXME); a VC joining a space is recorded with the admin as actor; a VC's own contribution via a resolver would reach `createActivity` with an empty actor id and fail the uuid constraint. Test: none. Spec: none. Ruling: should VC activity appear in the timeline, and as whose?
10. **Append-only rows with no foreign keys (ACT-17, ACT-26, ACT-61).** Code: deletions leave rows behind; readers drop them one by one, so `limit` counts rendered entries and feed pages can be short with a wrong total. Register: W4 F8 counts ~8,100 dangling rows on ACC and proposes "drop dangling, counted". Ruling: cascade or tombstone at write time in the new core (decision 8 of the register).
