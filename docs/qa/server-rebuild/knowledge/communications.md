## Where this lands in the new core

`room` becomes the `thread` anchor on every document kind (post, callout, calendar event, discussion, space updates, conversation) and the core itself becomes the Matrix AppService — "the rooms are the same rooms", so chat history is untouched and chat parity is checked on room ids per thread (`plan.md` § 1 facts, layer 6; catalogue CT-3, CM-1, CM-2, CM-3, CM-6). Every rule above stays valid as behaviour; what changes is that the post-send pipeline (COM-11/12/15/16/22) runs on the core's own Matrix event stream instead of an adapter echo, and the one SQL authorization verdict replaces the in-memory sender rule (COM-04/07) and the per-conversation participant snapshot (COM-54/57). Four facts found here should shape the model: (1) the row-before-room and row-before-delete orderings (COM-01/18, F1/F2) are the generator of register rows P1/P2/T1 — the new core must make room creation and deletion one unit of work or record the failure; (2) conversation membership is the only credential and is rebuilt on every join/leave (COM-54/57) — in the new core it is a plain membership relation that the verdict reads directly, which also decides who may delete a conversation (COM-59, F4); (3) consent to be messaged is one user setting with three enforcement shapes today (F7) — the new core should pick one; (4) the forum is a platform singleton whose categories are data and whose rooms are public to every authenticated user (COM-30/33/39/40) — the category vocabulary, admin-only set and the retirement guard are rules, the Matrix hierarchy reconcile (COM-43/44) is an operator tool that disappears when the core owns the hierarchy. Error texts, audit action names and policy-rule labels are rebaseline rows, not rules.
