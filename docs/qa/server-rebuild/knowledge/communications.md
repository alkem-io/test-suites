# Communications: behaviour rules

_What the platform does today for comments and messages, space updates, the forum, chat, and the Matrix plumbing behind them: what it does, why, who may, and what is still to answer. This file is the pilot of the three-section layout proposed in the product review (alkem-io/test-suites#717): **1. Rules**, **2. Rights**, **3. Open questions**, with the evidence in an **Appendix**._

_Open questions per owner: Product Lead 12 · Technical Lead 10 · Quality Lead 7 · Security Lead 3 · Incident Lead 2 · Service Operations Lead 2 · Architecture Lead 1. By state: 27 open · 10 with a suggested answer. Proof of the 61 rules: 30 proven by a test · 31 untested (Appendix A)._

**How to read it**

- **Rule** is one plain sentence. The exact behaviour, with error messages and limits, is in Appendix A under the same id. The new core is checked against the exact text.
- **Why: business** is what Alkemio needs. **Why: product** is the user story. **Why: technical** is the engineering reason, when there is one. "—" means no source states one and the product review gave none.
- **Decided by** names the source of the decision: a spec, a commit or pull request, or the product review. "Product review, Nov 2026" is the product pass of 2026-11-10 (alkem-io/test-suites#717) by the Product Owner CE, whose decisions stand on behalf of the Product Lead. "Not decided" means the behaviour exists in the code and nobody chose it.
- A marker in bold at the end of a rule points at section 3: **(open: F7)** means a question on this rule is still open, **(defect: F2a)** means today's behaviour is a fault and must not be copied as intended, **(defect in part: F3)** means part of it is. A rule with no marker stands as written. Every rule is logged as the server behaves today, also when that is not the intended end state. Whether a test proves the rule sits in Appendix A as **proven** or **untested**.
- Hard rules are not marked yet. Some rules are choices that a new feature may challenge, and some can never change; a later version will mark the second kind with "(hard rule)" after the why that makes it so. Until then, no marker does not mean a rule is open to change.
- A decision that changes what the server does today is not a rule yet. It stays in section 3 with the state **change decided** and an issue link until it ships. None exists in this file today.
- A decided question leaves section 3 and moves onto its rule; "was F4" in **Decided by** keeps the trail.

### F. Where this lands in the new core

`room` becomes the `thread` anchor on every document kind (post, callout, calendar event, discussion, space updates, conversation) and the core itself becomes the Matrix AppService — "the rooms are the same rooms", so chat history is untouched and chat parity is checked on room ids per thread (`plan.md` § 1 facts, layer 6; catalogue CT-3, CM-1, CM-2, CM-3, CM-6). Every rule above stays valid as behaviour; what changes is that the post-send pipeline (COM-11/12/15/16/22) runs on the core's own Matrix event stream instead of an adapter echo, and the one SQL authorization verdict replaces the in-memory sender rule (COM-04/07) and the per-conversation participant snapshot (COM-54/57). Four facts found here should shape the model: (1) the row-before-room and row-before-delete orderings (COM-01/18, F1/F2) are the generator of register rows P1/P2/T1 — the new core must make room creation and deletion one unit of work or record the failure; (2) conversation membership is the only credential and is rebuilt on every join/leave (COM-54/57) — in the new core it is a plain membership relation that the verdict reads directly, which also decides who may delete a conversation (COM-59, F4); (3) consent to be messaged is one user setting with three enforcement shapes today (F7) — the new core should pick one; (4) the forum is a platform singleton whose categories are data and whose rooms are public to every authenticated user (COM-30/33/39/40) — the category vocabulary, admin-only set and the retirement guard are rules, the Matrix hierarchy reconcile (COM-43/44) is an operator tool that disappears when the core owns the hierarchy. Error texts, audit action names and policy-rule labels are rebaseline rows, not rules.
