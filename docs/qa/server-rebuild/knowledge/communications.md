# Communications — behaviour knowledge (v2 pilot: three whys, routed manual points)

_Extracted 2026-11-06 from three sources: server develop @ `eeecf9ddb` (Release/79) code + `schema.graphql`; the legacy server-api suite (`server-api/src/functional-api/communications/`, 12 files, 123 cases — 7 `skip`, 9 more gated to a local Postgres / Redis / Synapse and never run on the nightly); the specs, issues and docs listed in § Sources. Restructured 2026-11-09 as the pilot of the shape agreed with the product team: the single why column is split into **Why — product** (what the organisation wants to be true: revenue, trust, moderation, legal, coherence — owned by the Product circle), **Why — user** (what the end user gains or is protected from, in the user's own terms — the "so that" of a spec user story) and **Why — technical** (the engineering reason, only when one exists and matters); and every manual point in Findings, Gaps and Open questions is filed under the role that must answer it. Rooms and messages, community updates, forum discussions, direct and group conversations, Matrix sessions and the communication admin operations. Callout-level comment enabling is CAL-24 in `callout.md`; chat-message notifications are the notifications area (034) — both cross-referenced, not redone; `033-chat-avatars` is presentational and only listed. WHAT and WHY only — no mutations, fixtures or request params. Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". A why cell reading "—" means no source states one; nothing in a why cell is invented — each is traceable to a spec user story, FR, decision, commit or code comment named in the row's Sources or in the dossier. Evidence paths are relative to the server repo unless prefixed `test ›`, `spec ›`, `matrix ›` or `register ›`._

_Review load: 16 findings · 13 unknown-why rows (all three why cells empty — the 7 original plus COM-09/16/18/22/41/42/59, whose old why was only an origin or a dispute pointer) · 7 rows with a product why but no user why (COM-15/34/37/45/55/66/69) · 19 untested rows (gaps) · 35 constants to tick (each pre-routed in "Rules on it") · 8 open questions. Manual points sit in five places: the Findings, the `unknown-why` rows, the `untested` rows (repeated under Gaps), the "product must rule?" column of the constants, and the Open questions — and every Finding, Gap and Open question now sits under the role that answers it._

## Where this lands in the new core

`room` becomes the `thread` anchor on every document kind (post, callout, calendar event, discussion, space updates, conversation) and the core itself becomes the Matrix AppService — "the rooms are the same rooms", so chat history is untouched and chat parity is checked on room ids per thread (`plan.md` § 1 facts, layer 6; catalogue CT-3, CM-1, CM-2, CM-3, CM-6). Every rule above stays valid as behaviour; what changes is that the post-send pipeline (COM-11/12/15/16/22) runs on the core's own Matrix event stream instead of an adapter echo, and the one SQL authorization verdict replaces the in-memory sender rule (COM-04/07) and the per-conversation participant snapshot (COM-54/57). Four facts found here should shape the model: (1) the row-before-room and row-before-delete orderings (COM-01/18, F1/F2) are the generator of register rows P1/P2/T1 — the new core must make room creation and deletion one unit of work or record the failure; (2) conversation membership is the only credential and is rebuilt on every join/leave (COM-54/57) — in the new core it is a plain membership relation that the verdict reads directly, which also decides who may delete a conversation (COM-59, F4); (3) consent to be messaged is one user setting with three enforcement shapes today (F7) — the new core should pick one; (4) the forum is a platform singleton whose categories are data and whose rooms are public to every authenticated user (COM-30/33/39/40) — the category vocabulary, admin-only set and the retirement guard are rules, the Matrix hierarchy reconcile (COM-43/44) is an operator tool that disappears when the core owns the hierarchy. Error texts, audit action names and policy-rule labels are rebaseline rows, not rules.
