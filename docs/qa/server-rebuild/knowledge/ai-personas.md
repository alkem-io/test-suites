## Where this lands in the new core

The catalogue lands AI-2 in the "ai_engine registry" (slices 10–12, verdict absent, "admin-only; decide with the backend team whether it survives"). A persona today is one row per VC plus a stand-alone path nobody reaches; in the rebuild it becomes a registry entry (engine, prompt, prompt graph, external configuration) referenced by the VC's `actor` row, with no stored authorization policy and no reset (AIP-02/03 disappear; AIP-06's "inherit the VC" becomes the only rule, evaluated at read time). RabbitMQ goes, so AIP-11/12/15/16 — the queue-per-engine routing, the history assembly from Matrix, the result event — need a replacement transport that the deck does not name; and with chat moving browser → Synapse the server will no longer see room messages to build a history from (AIP-12). Three facts should shape the registry: (1) the enum carries engines that cannot be reached (F-3) — the registry should list only deployable engines; (2) secrets are handled per persona with a leak on read (F-4) — the registry needs a write-only secret column; (3) `defaultAiPersona` and the stand-alone create path have no user (F-1, AIP-07) — candidates for the expected-loss list rather than migration.

## Findings (sources disagree, or likely defect)

1. **The default persona can never be read (AIP-04).** Code: `aiServer.defaultAiPersona` is a non-null GraphQL field backed by a relation nothing writes; the resolver throws "No default Virtual Personas found!". Test/spec: none. Ruling: drop the field or seed a default.
2. **Persona and VC can orphan each other (AIP-10).** Code: `aiPersonaID` is a bare uuid column; deleting a persona leaves the VC pointing at nothing (every question then fails), and VC deletion deletes the persona best-effort. Register E5: 159 personas without a VC on acceptance. Ruling: FK with cascade in the new model; a repair for E5.
3. **An engine value with no queue (AIP-11).** Code: the enum has `community-manager` and `openai-assistant`; queues exist for `openai-assistant` but not `community-manager` (decommissioned 2026-08-04), so a persona on that engine publishes into the void with no error. `openai-assistant` is excluded from the externally-configurable list and its repo is archived (2026-05-28). Ruling: shrink the enum to live engines and refuse creation/updates on retired ones.
4. **External configuration leaks to persona readers (AIP-09).** Code: `externalConfig` is returned for generic-openai/libra-flow personas to anyone with READ on the persona, which the persona inherits from the VC — for a public VC that is every visitor; `apiKey` is masked by a field resolver but `assistantId` has none and resolves to the stored ciphertext, and `model` is in clear. Test/spec: none (004 FR-007 covers the assistant only). Ruling: restrict `externalConfig` to the VC's account admin and platform content roles, and never return `assistantId` ciphertext.
5. **`aiServer` root query is ungated (AIP-01).** Code: returns the singleton (id, dates) to anonymous callers; every field is READ-gated so only the id leaks. Mirrors CM finding 7 / VCK F-7. Ruling: gate or accept.
6. **Updating a persona never re-ingests (AIP-08).** Code: "TBD: trigger a re-ingest?" — a changed engine or prompt keeps the old vectors. Ruling: define when ingest must re-run.
7. **History role detection by chat-id prefix (AIP-13).** Code: a message is "the assistant's" iff the sender id starts with `@virtualcontributor` — any VC, not the asked one, and dependent on the adapter's naming convention. Ruling: accept as convention or mark messages by actor type.
8. **Persona mutations log as organisation actions (AIP-10).** Code: `aiServerUpdateAiPersona` / `aiServerDeleteAiPersona` label their authorization check `orgUpdate` / `deleteOrg`; neither writes a platform audit row although content-full-access reaches them. Ruling: audit + relabel.

## Gaps (no legacy case)

Untested rules by id: AIP-04, AIP-06, AIP-07, AIP-08, AIP-09, AIP-10, AIP-11, AIP-12, AIP-13, AIP-14, AIP-15, AIP-16, AIP-17, AIP-19, AIP-20; plus the untested clauses of AIP-01 (ungated root read), AIP-02 (PCFA CRUD cells), AIP-03 (audit row), AIP-05 (prompt limits), AIP-18 (effect on a stack with a vector store).

Behaviours the area has that neither reading nor tests pinned down:
- A question answered end to end on a stack with an engine (publish → worker → result → reply) — no environment the suite runs on has the worker (a11 accepts "fetch failed" for the vector store).
- Creating, updating and deleting a stand-alone persona (all three mutations unreached; catalogue AI-2).
- Persona update through the VC owner (account admin) — the policy says yes; never exercised.
- Prompt limits (11th line, over-long line) and the external-config merge (partial update keeps the stored key).
- Prompt graph null-clear versus partial merge.
- History assembly: thread versus room, the 30 cap with and without the entity content, the sender-prefix rule.
- Reading `externalConfig` as a non-admin reader of a public generic-openai VC (F-4 repro).
- Vector-store cleanup effect (needs Chroma).

## Open questions (could not be determined from the three sources)

Someone must say which workers run on acceptance/production and which enum values should be refused.
2. **Does the engine honour what the server sends** — `language`, `contextID`, `interactionID`, `operation: ingest`, the prompt-graph override? Engine code not read.
3. **Live confirmation of F-4** (ciphertext `assistantId` to an anonymous reader of a public generic-openai VC).
4. **Was `defaultAiPersona` ever populated** on any environment (a DB read of `ai_server.defaultAiPersonaId`)?
5. **Is there any budget for VC usage** outside the server (per-engine rate limits in the worker, provider quotas)? The server has none (AIP-19); product may believe there is one.
