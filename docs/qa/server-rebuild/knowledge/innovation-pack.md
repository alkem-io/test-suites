## Where this lands in the new core

The briefing folds packs and hubs into the space document — "space.kind hub / pack" (catalogue CT-15, slices 10–12, marked **partial**: "API thin (1 + few cases); no UI; W2 journey 12") — so a pack becomes a space-like container whose scope is an account and whose content is a set of blueprints (templates). Every rule above survives as a behaviour: account ownership and the single-entitlement model (IPK-01), the provider as the account host (IPK-04), the support/PCFA/PRA split on update, delete and move (IPK-05–07), the three visibilities and the viewer-scoped lists (IPK-09), and the library's eligibility, ordering and search (IPK-11). What should change shape: (1) visibility today is a listing filter layered over a world-readable policy (IPK-10, finding 2) — in a core without stored policies the scope rule must decide read access, not only list membership, or the "hidden" visibility stays decorative; (2) the pack's policy is a clone of the account's (IPK-14) — a scope on the account suffices; (3) the global pack name-id and the per-set template name-id (TPL-03) become one alias rule under `resolve(url)`; (4) the "number of templates" used for ordering (IPK-11) must count every blueprint kind. Error texts are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **The area's only legacy case asserts nothing and does not run (IPK-01, IPK-13).** Test: `innovation-pack.it-spec.ts` creates an organisation, a pack and six whiteboard templates and ends with `expect(200).toBe(200)`; its `afterAll` delete is commented out, so every run leaks an organisation and a pack; it passes the **organisation id** as the pack's `accountID`, which the server would refuse; and the `innovation` vitest project is not in the nightly glob. Ruling: retire the case and let the entitlements, account and platform-roles suites carry the proof — or rewrite it as a real create/read-back/delete case on the organisation's account.
2. **"Hidden" hides a pack from lists, not from readers (IPK-09, IPK-10).** Code: the pack policy inherits the account's, which grants READ to anonymous and registered (`account.service.authorization.ts:306-310`, "TODO: work through the logic"); `hostedResources` filters by viewer scope but says "authorization policies are deliberately not consulted"; `Account.innovationPacks` on the world-readable `lookup.account` returns hidden packs to anyone; `lookup.innovationPack(ID)` answers for anyone. Test: `hosted-resources` proves the filtered list only. Spec: the enum says hidden "only shows up when directly accessed e.g. by provider" — the "e.g. by provider" implies the provider, not the world. Ruling: is a hidden or account-scoped pack meant to be unreadable to outsiders who hold its id (then this is a defect, kin to entitlements finding 5), or is visibility purely a discovery hint?
3. **A pack cannot be created with its intended visibility (IPK-03).** Code: `createInnovationPack` hard-codes listed + account-scoped and the input carries no visibility fields; the bootstrap comment records that the seed must re-save the pack public after creating it (`bootstrap.service.ts:751-755`). Test: none. Spec: none. Ruling: accept `listedInStore` / `searchVisibility` on create, or keep the two-step as the rule.
4. **The library's "number of templates" and the pack count exclude classification templates (IPK-11).** Code: `getTemplatesCount` sums five kinds (`templates.set.service.ts:238-276`); a pack holding only classification templates (the seeded one) sorts last with 0. Shared with `templates.md` finding 1. Ruling: count all six kinds.
5. **A transfer ignores the target account's pack allowance (IPK-07).** Code: `validateTransferOfAccountResource` checks offer/accept only; `validateSoftLicenseLimitOrFail` is not called. Test: `transfer-innovation-pack-to-account` › the first case is titled "…without valid entitlements" and passes — the suite enshrines it. Spec 027 A9: silent on limits. Ruling: intended (a move is not a creation), or a gap in the cap?
6. **Owner deletes and moves leave no audit trail (IPK-06, IPK-07).** Code: the platform branch audits (027 T058 / FR-018a "audit ONLY on the PLATFORM branch"); an account admin deleting their own pack writes nothing; a deleted pack's templates vanish with it. Ruling: by design today — record, or extend the audit to owners before the cutover's activity model.
7. **A stale log says the library ignores its query options (IPK-11).** Code: `library.resolver.fields.ts:37-40` logs "Ignoring query data … for now; to be added back in later" and then passes `limit` and `orderBy` to the service, which honours them. Cosmetic; ruling: delete the log so operators do not read the wrong contract.

## Gaps (no legacy case)

Untested rules by id: IPK-02, IPK-03, IPK-05, IPK-06, IPK-11, IPK-12, IPK-13, IPK-14, IPK-15; plus the untested clauses of IPK-09/10 (direct read of a hidden pack by an outsider; `Account.innovationPacks` filter), IPK-07 (policy recomputation after a move — a template in the moved pack read by the new owner), IPK-01 (PCFA creating on someone else's account; PLM bypass — see ENT-41).

Behaviours the area has that neither reading nor tests pinned down:
- Updating a pack: rename (name-id collision refusal), un-listing, switching visibility and reading the library before/after — no API case; `hosted-resources` flips visibility only as setup.
- Deleting a pack that holds templates in use as a flow-state default elsewhere (TPL-17) or whose templates were applied to spaces (nothing links back — expected no effect).
- Deleting an organisation that hosts a pack (the organisation-side blocker; only the user self-delete blocker is proven).
- The library pages themselves: ordering by template count, the 100 cap, the search term, pagination consistency (101 FR-007/008) — unit specs only.
- Name-id derivation when two packs with the same display name are created concurrently (W4 C2 class of defect).
- An innovation hub's curated pack list respecting visibility (IPK-15).
- Authorization reset of a pack after its account's host changes (organisation admin removed; user deleted — pack cascades with the account row, `onDelete: CASCADE`).

## Open questions (could not be determined from the three sources)

Read-only extraction against the code, the tests and the specs; nothing below could be settled without a live stack or a source outside the three. Each needs a person to answer it or route it.

1. **Which credentials the harness admin holds.** The transfer suite and the smoke case run as `GLOBAL_ADMIN`; whether the persona is PRA / PCFA by fixture decides what those green rows prove (same question as every other table).
2. **Live read of a hidden pack by an outsider.** Finding 2 is a policy reading (`access-matrix.md:949-985` agrees: anonymous READ). Confirm on a stack: `lookup.innovationPack(ID)` of a `hidden` pack as anonymous, and `lookup.account(ID).innovationPacks` as an unrelated user.
3. **Is global pack name-id uniqueness intended?** Spaces and templates scope their name ids; packs do not (IPK-02). No spec states either; product should say which the new alias rule follows.
4. **Does the client rely on the library's default ordering?** IPK-11's "most templates first" is a code default; the paginated fields use insertion order instead (101 FR-015). Decide which the new core keeps.
5. **Has the smoke case ever been green?** It passes an organisation id where an account id is required (finding 1); either the harness's `createOrganization` once returned an account-shaped id, or the case has been red/unrun since the account model landed. Check the last `innovation` project run.
