# Callouts: behaviour rules

_What the platform does today for callouts: creating and framing them, their settings, publishing and closing, contributions, posts and comments, Forms, polls, reactions, the Contributors and Subspaces collections, transfer, deletion and reading: what it does, why, who may, and what is still to answer. The layout is the three-section one of `communications.md`: **1. Rules**, **2. Rights**, **3. Open questions**, with the evidence in an **Appendix**._

_Open questions per owner: Product Lead 3 · Technical Lead 8 · Quality Lead 8 · Security Lead 1 · Architecture Lead 4. By state: 10 open · 3 change decided · 11 with a suggested answer · 9 decided. Proof of the 77 rules: 45 proven by a test · 32 untested (Appendix A)._

_Whys of the 77 rules: all 77 rest on a source or a product decision · 1 technical why is still a QA draft, for the Technical Lead (CAL-03, see Q-CAL-03)._

**How to read it**

- **Rule** is one or two plain sentences. The exact behaviour, with error messages and limits, is in Appendix A under the same id. The new core is checked against the exact text.
- **Why: business** is what Alkemio needs. **Why: product** is the user story. **Why: technical** is the engineering reason. A rule needs at least one why, and gets a second or third only where it adds something for the decision or the code. "—" means none is given.
- A why that names a spec, issue, pull request, code comment or code line rests on that source. A why, or the part of a why, ending in _(draft)_ was written by QA and no source states it: product keeps, rewrites or deletes it, and sets **Decided by**. A user story always ends in its "so that"; where no source gives one, QA wrote it. A rule with no why at all carries an open question in section 3.
- **Decided by** names the source of the decision: a spec, a commit, a pull request or an issue. "Not decided: exists in the code" means the behaviour is in the code and nobody chose it in a source we could find.
- A marker in bold at the end of a rule points at section 3: **(open: F3)** means a question on this rule is still open, **(defect: F2)** means today's behaviour is a fault and must not be copied as intended, **(defect in part: F5)** means part of it is. A rule with no marker stands as written. Every rule is logged as the server behaves today, also when that is not the intended end state. Whether a test proves the rule sits in Appendix A as **proven** or **untested**.
- Hard rules are not marked yet. Some rules are choices that a new feature may challenge, and some can never change; a later version will mark the second kind with "(hard rule)" after the why that makes it so. Until then, no marker does not mean a rule is open to change.
- A decided question leaves section 3 and moves onto its rule; **Decided by** then keeps the trail.
- In the product a callout is shown to users as a "Post". This file says "callout" for it and "post" for the post that a member adds to a callout.

#### Findings

- **F1 — Per-type contribution rights are never checked (CAL-27, CAL-37).** Code: `allowedTypes` grants `create-post` / `create-whiteboard` / `contribute` rules on the callout, memo none (crosscheck F10), but every contribution mutation gates on `contribute` only; `CREATE_POST` and `CREATE_WHITEBOARD` are checked nowhere. Ruling: one right for all types (then drop the derived rules), or real per-type rights (then add memo and gate them). **Product, 2026-11-20:** types need no rights of their own; the design choice stays with the Architecture Lead.
- **F2 — Framing comments cannot be switched off server-side (CAL-24).** Code: `framing.commentsEnabled` only decides room creation and attachment auth; the room policy is always built. Test: the only cases (`close-state › Discussions`, expecting `CALLOUT_CLOSED` / `FORBIDDEN_POLICY`) are `describe.skip`. Client plan :724-726 only hides the input. Data: audit register F1 — 866 collection callouts on ACC carry `commentsEnabled: true` with no room (2026-07-08 migration); the server creates the room on each one's next edit. Ruling: should collection callouts have comments (create the rooms) or not (fix the flag), and should disabling comments refuse messages? **Product, 2026-11-20:** the server refuses comments while they are off; the 866 collection callouts get the flag switched off (change decided).
- **F3 — Draft readers: admins + creator, not leads (CAL-19).** Code grants draft READ to the admin credentials (with parents) and the creator; the client plan (`plans/callouts-test-plan.md:34-35`) says "admins/leads". No case pins a lead either way. Ruling: are leads meant to see drafts? **Product, 2026-11-20:** leads do not see drafts; the client plan is wrong.
- **F4 — `transferCallout` claims the executor becomes the creator (CAL-70).** Schema description (`callout.transfer.resolver.mutations.ts:23`, PR #4914) vs. code: the transfer module never writes `createdBy`, so the original creator keeps CREATE/READ/UPDATE/DELETE on the moved callout in its new space. Ruling: fix the description or the code.
- **F5 — Transferred callout stranded on a vanished phase (CAL-71).** After the destination's flow was replaced by a template, the callout keeps the pre-template default phase that no longer exists (`transfer-callout-template-flow` ×2 `test.skip`, server#4970 / client-web#9353). Ruling: defect, already filed; keep the skip until fixed.

### F. Where this lands in the new core

`callout` is a document kind with a `framing` sum type and a `contributions` relation; `settings` becomes typed columns, not a JSONB blob merged by hand (CAL-12's null and array rules disappear with the blob). Three things found here should shape the model: (1) the per-type contribution rights are decorative today — the new core should either gate per type (and give memo one) or drop the derived privileges and keep the single contribute right (CAL-27, F1); (2) visibility, lock state and framing comments are three independent flags whose enforcement differs (draft rewrites read; lock is checked in one resolver; comments are not enforced at all) — the new core should enforce all three at the same layer (CAL-19/23/24, F2); (3) the collection kinds (Contributors, Subspaces) and the intake kind (Form) are read-time computed or privacy-scoped views with no stored policy — the Form's per-request audience evaluation (CAL-47) is the pattern the new core's `viewer`-scoped reads should follow, and the manual-selection scope guard (CAL-64) and shrink-only render (CAL-66) are invariants, not implementation. Transfer (CAL-70) is a support tool that re-parents a document; with a single store it becomes a parent change plus a classification re-sync, and the activity-log re-stamping goes away. Reactions, votes and responses are each one row per person per target with a unique key — the new core keeps the three upserts and drops the "created vs swapped" timestamp heuristic (`reaction.service.ts:70-75`). Error texts and codes are rebaseline rows, not rules; the Form's `extensions.details.code` convention is the one worth keeping platform-wide.
