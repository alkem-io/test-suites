## Where this lands in the new core

`license_plan`, `plan_entitlement`, `plan_assignment`, resolved at read time; no per-entity licence cache and no reset mutations. Platform feature roles become credentials scoped by target type. Every rule above stays valid as a behaviour; what changes is that ENT-05/06/27 no longer need a reset step (today they already recompute inline, but through a stored snapshot — ENT-14), and that the entitlement read moves from the account query to the `viewer` slice. Three facts found here should shape the model: (1) the plus-granting feature roles are not policy rules but a credential issued on role change (ENT-01/08) — in the new core they should become ordinary plan assignments with a role-derived source; (2) space flags are evaluated from the L0 agent only, so `plan_assignment.target` must be constrained to L0 (ENT-26, F-3); (3) trial expiry must be part of the read-time resolution (ENT-25, F-2). Error texts are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **Free tier never issued (ENT-13/15).** Code: the policy carries an `account-license-free` rule (1 free space, 1,000,000 AI tokens) but no plan issues that credential and the credential enum omits it — a plain account has zero of everything. Test: `No licenses assigned` cases pin `availableEntitlements: []`, enshrining it. Spec: 004 FR-027 expects a free-tier budget "or the configured platform default"; the AI migration records a signed-off 1M free allowance. Ruling: is a plan-less account meant to be able to create nothing, and where does the free AI budget come from?
2. **Trial expiry is decorative (ENT-25).** Code: `SPACE_LICENSE_PLUS` is issued with `expires = +1 month`, but the engine matches credential types only and nothing prunes or filters expired credentials. Test: none. Spec: none. Ruling: defect to fix, or trial expiry is handled by a human revoke?
3. **Subspace plan assignment silently inert (ENT-26).** Code: no L0 check on `assignLicensePlanToSpace`; entitlements are computed from the L0 agent. Test: none. Spec 083: L0-only, enforced by the client's License Issuer. Ruling: server must refuse non-L0 targets, or document the client as the gate.
4. **`SPACE_LICENSE_ENTERPRISE` grants nothing (ENT-24).** Code: plan exists, no rule, enum comment "todo: remove". Test/spec: none. Ruling: remove or define.
5. **Any visitor can read any account's licence, limits, usage and subscriptions (ENT-44).** Code: account policy grants READ to anonymous + registered with a TODO. Test: only own-account reads. Spec: none. Ruling: privacy — should another account's plan and usage be visible?
6. **Hub entitlement available but unusable by its holder (ENT-16/39).** Code: plus grants 1 hub; the account admin never holds `CREATE_INNOVATION_HUB`. Test: asserts the hub type is in the available list; never creates one. Spec 027 QA C1-12: hubs platform-curated. Old ENT-01 implied the user could create a hub. Ruling: accepted; the knowledge row now says so — but the client should not offer a "create hub" button on the strength of `availableEntitlements`.
7. **Limit error text embeds the account id (ENT-02/03/04).** Code: `account.resolver.mutations.ts:721` contradicts the repo rule against dynamic data in exception messages. Test: three cases pin the exact string with the id. Ruling: when the message is cleaned, rebaseline the three cases; do not treat the red as a behaviour change.
8. **Save-as-template flag is never enforced (ENT-33).** Code: computed on space + collaboration, no reader. Test/spec: none. Ruling: dead flag or missing gate?
9. **Create-time defaults differ between space and collaboration (three flags `enabled:true/limit:0` on the space, `false` on the collaboration).** Harmless today because `createSpace` recomputes at once; spec 083 documents gating on `limit`. Ruling: single default in the new core.
10. **FLAG rules ignore their `limit`; account rules sum it; only the first matching rule counts.** Code: `space.service.license.ts:120-123` vs `account.service.license.ts:112`; `licensing.credential.based.service.ts:86-99`. Latent until a second account plan exists. Ruling: define `limit` semantics for the new core.
11. **Stale comment vs signed-off numbers.** `license.entitlement.type.ts:19-23` says the AI-token values are placeholders; the migration says signed off 2026-06-17. Ruling: trust the migration; fix the comment.
12. **Invitation path for VC Campaign unverified (ENT-37).** Code read only covers the direct `assignPlatformRoleToUser` sync; whether accepting a platform invitation carrying `feature-vc-campaign` also issues the plus credential was not confirmed. Ruling: verify live, then mark ENT-01 for the invitation path.
13. **Organisation VC access hard-off "for now" (ENT-34).** No product statement. Ruling: are VCs ever organisation members?

Behaviours the area has that neither reading nor tests pinned down:

- What a space loses when `SPACE_LICENSE_PLUS` is revoked while multi-user whiteboards are in use (session behaviour).
- Plan assignment by a non-PLM actor being refused (the gate exists; only the platform-roles suite covers it).
- The account-plan / space-plan family mismatch refusal (ENT-18).
- A second account plan (premium) — none exists; summing across credentials is unexercised.
- Baseline plan raise/lower and its interaction with a plan credential on the same account.
- `licenseResetOnAccount` / `resetLicenseOnAccounts` leaving state unchanged (idempotence).
- Organisation-hosted spaces inheriting anything from the organisation's account plan (they do not — the space's own L0 credentials decide; still worth one case).
- The L1→L0 conversion path (`journey/conversion/convert-L1-to-L0-basic.it-spec.ts` touches it) — which plans a converted space receives.
- Audit rows for assign/revoke/baseline/definition actions.

## Open questions (could not be determined from the three sources)

Read-only extraction against the code, the tests and the specs; nothing below could be settled without a live stack or a source outside the three. Each needs a person to answer it or route it.

1. **Which credential lets the harness assign plans.** The legacy cases assign plans as the `GLOBAL_ADMIN` persona and are green, but the gate is platform-license-manager only (ENT-47). Either the persona holds that role on the test stack or the gate is not what the code says. Check the persona's roles on the test cluster.
2. **Other grant paths for the plus credential.** Only the direct `assignPlatformRoleToUser` path was read (ENT-01). Whether granting a feature role to an organisation, or accepting a platform invitation that carries VC Campaign (ENT-37), also issues `ACCOUNT_LICENSE_PLUS` is unread — see finding 12.
3. **Is the order of `availableEntitlements` a contract?** The tests sort before comparing; the code gives no ordering guarantee. Decide whether the new core must preserve an order.
4. **Live confirmation of finding 2.** That an expired plus trial keeps granting is a code reading; nobody has watched a trial cross its expiry on a running stack.
