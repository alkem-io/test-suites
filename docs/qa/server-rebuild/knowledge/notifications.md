Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". Evidence paths are relative to the server repo unless prefixed `test ›` or `spec ›`._

## Where this lands in the new core

Notifications are the registry-driven slice of rebuild slices 8–9 ("threads, notifications, activity"): a `notification_kind` registry with, per kind, its recipient rule (member / admin / lead / single actor / platform role), its scope policy, its settings key and its channel set — the table above is that registry written out. Three things found here should shape the model: (1) recipient resolution is one pipeline (NTF-10) and every kind must be in it or in the explicit bypass list — the five "fixed-channel / bypass" kinds (NTF-27, 28, 35, 56 receipt, 67) are the exceptions to encode, not to forget; (2) the suppress-on-replacement rule (NTF-32/33/66) and the actor-exclusion exceptions (NTF-16) are product rulings that must be first-class flags on the kind, not adapter code; (3) the chat digest (NTF-70..77) is a scheduler, not a notification kind — the new core keeps the four-track debounce as its own component feeding two kinds, with Redis state as a hint only. Settings become one row per kind per user with per-channel booleans and mandated defaults carried by the registry, so "defend on read" (NTF-05) disappears. Email subjects, push copy and windows are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **The sender's copy of an organization message is governed by the "application received" space-admin row (NTF-61).** Code: `ORGANIZATION_MESSAGE_SENDER` shares the `space.admin.communityApplicationReceived` case (`notification.recipients.service.ts:508-511`), so a sender who has muted "someone applied to my space" also loses their "Message sent" confirmation, and a sender who never administers a space still has the row (default on). Test: `user-to-organization` asserts exactly 3 admin mails and no sender mail — the sender persona's row state is not controlled, so the case passes by accident of harness settings. Spec: none names a row for the sender copy. Ruling: give the sender copy its own row, or drop it; rebaseline the 3 counts.
2. **The creator of a forum discussion is notified of their own discussion (NTF-51).** Code: no actor filter on email or in-app for `PLATFORM_FORUM_DISCUSSION_CREATED` (`notification.platform.adapter.ts:194-233`), while push filters the creator (`:236-238`). Test: `forum-discussions` › `QA create forum discussion - GA(1), QA(1)…` enshrines the self-email. Spec: none. Ruling: self-notification intended? If not, fix and rebaseline the two counts.
3. **Awareness platform-admin kinds drop the actor from push only (NTF-16/22).** Code: `platformUserProfileCreated` and `platformSpaceCreated` filter `triggeredBy` from push (`notification.platform.adapter.ts:478-480, 414-416`) although the routing row says `excludeActor: false` and 065 FR-012 says the exclusion must not apply. Test: the routing suite proves the recipients query keeps the actor on all three channels, but no live case observes the push emit. Ruling: remove the two push filters (one owner, per 065 FR-011) or amend FR-012.
4. **Two recipient models for organization admins (NTF-13/61).** Code: legacy message and mention kinds take `ORGANIZATION_ASSOCIATE` candidates filtered by the org admin privilege (admins and owners who are associates); the 2026-09 kinds take ADMIN standing (admin-not-associate included, owner excluded) — `notification.recipients.service.ts:997-1043`. Test: both models are proven separately. Spec: 061 records the owner question as open product. Ruling: one audience for all organization kinds.
5. **An organization admin who messages their own organization is told about it (NTF-61).** Code: `organizationSendMessage` filters the sender from push only (`notification.organization.adapter.ts:181-183`); email and in-app include them. Test: senders in `user-to-organization` are never admins. Ruling: apply NTF-15.
6. **Organization mentions: "disabled since 2025-08-22" vs live code (NTF-50).** Code: `ORGANIZATION_ADMIN_MENTIONED` is dispatched for every org mention with a live settings row (`room.mentions.service.ts:148-160`). Test: `mention-organization` is `describe.skip` with six todos saying the feature is disabled and "not migrated to user settings". Ruling: confirm live whether an org mention notifies; retire the annotation or the code.
7. **VC invitation declined goes to the inviter only, and to nobody when the inviter is gone (NTF-37).** Code comment records the asymmetry with the four other outcome kinds as deliberate but unruled (`notification.recipients.service.ts:772-786`). Ruling: align with NTF-32 (every admin) or keep.
8. **Owners who are not admins act but are never notified (NTF-13/38/64).** Carried from 061/062 as an open product question (owners can accept / decide from the tab, get no email, have no settings row). Ruling: product.
9. **Retention constants are not enforced (NTF-84).** Code: 90 days / 100 per user are applied only when an operations admin runs the prune; no cron, no startup job (`in.app.notification.admin.service.ts`). Spec: #5397 (not read). Ruling: is pruning operated (k8s job on the internal-admin endpoint), or are the constants decorative?
10. **Callout-comment in-app payload writes the commenter's id into `contributionID` (NTF-47/80).** Code: `notification.space.adapter.ts:906` (`contributionID: eventData.triggeredBy`), documented in the DTO as intentional (`notification.in.app.payload.space.collaboration.callout.comment.ts:11`); the FK column is not populated for this kind so nothing breaks, but the field name lies to the client. Ruling: rename or drop in the new core.
11. **Chat in-app row kept "for shape symmetry" but forced off (NTF-71).** Code stores `conversationMessage*.inApp` and never honours it; the public API accepts `inApp: true`. Test: proven. Ruling: accepted (034 D-2) — record as a rule, not a bug; the new core should drop the dead leaf.
12. **Whiteboard callout publication case skipped.** Test: `callouts` › `HA create PUBLISHED space callout type: WHITEBOARD` is `test.skip` expecting 7 mails where every other publish case expects 6 (publisher excluded). Code: no framing-specific difference for publish. Ruling: the skip hides an expectation that contradicts NTF-15; delete or fix the case.
13. **Mention of a user by a non-member is refused upstream (NTF-50).** Test: `Non Space member mention HM in Space comments callout - 0 notification` passes because the comment itself is refused (callout access), not because mentions are gated by the sender's membership. Code: `userMention` has no sender-membership check. Ruling: the case is a callout rule in disguise; move it.
14. **Platform-invitation dead duplicate.** Code: `notification.space.adapter.ts:1391-1411` duplicates `notification.platform.adapter.ts:354-374` with no caller (081 KG-4). Ruling: delete.
