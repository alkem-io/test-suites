# Notifications: behaviour rules

_What the platform does today for email and in-app notifications: the kinds, who receives them, the settings, what is held back, the chat digests, and what is still to answer. How the push channel itself works is in `push-notifications.md`. The layout is that of `communications.md`: **1. Rules**, **2. Rights**, **3. Open questions**, with the evidence in an **Appendix**. Product has not reviewed this file yet._

_Open questions per owner: Product Lead 12 · Technical Lead 4 · Quality Lead 11 · Service Operations Lead 2 · Architecture Lead 2. By state: 26 open · 5 with a suggested answer. Proof of the 75 rules: 54 proven by a test · 21 untested (Appendix A)._

_Whys of the 75 rules: 56 rest on a source · 16 carry a draft for product to decide · 3 have none, and each already carries an open question (NTF-36, NTF-52, NTF-82)._

**How to read it**

- **Rule** is one or two plain sentences. The exact behaviour, with error messages and limits, is in Appendix A under the same id. The new core is checked against the exact text.
- **Why: business** is what Alkemio needs. **Why: product** is the user story. **Why: technical** is the engineering reason. A rule needs at least one why, and gets a second or third only where it adds something for the decision or the code. "—" means none is given.
- A why that names a spec, issue, pull request, code comment or code line rests on that source. A why ending in _(draft)_ was written by QA and no source states it: product keeps, rewrites or deletes it, and sets **Decided by**. A rule with no why at all carries an open question in section 3.
- **Decided by** names the source of the decision: a spec, a commit, a pull request or an issue. "Not decided: exists in the code" means the behaviour is in the code and no source shows that anybody chose it.
- A marker in bold at the end of a rule points at section 3: **(open: F2)** means a question on this rule is still open, **(defect: F2)** means today's behaviour is a fault and must not be copied as intended, **(defect in part: F2)** means part of it is. A rule with no marker stands as written. Every rule is logged as the server behaves today, also when that is not the intended end state. Whether a test proves the rule sits in Appendix A as **proven** or **untested**.
- Hard rules are not marked yet. Some rules are choices that a new feature may challenge, and some can never change; a later version will mark the second kind with "(hard rule)" after the why that makes it so. Until then, no marker does not mean a rule is open to change.

#### Findings

- **F1 — The sender's copy of an organization message is governed by the "application received" space-admin row (NTF-61).** Code: `ORGANIZATION_MESSAGE_SENDER` shares the `space.admin.communityApplicationReceived` case (`notification.recipients.service.ts:508-511`), so a sender who has muted "someone applied to my space" also loses their "Message sent" confirmation, and a sender who never administers a space still has the row (default on). Test: `user-to-organization` asserts exactly 3 admin mails and no sender mail — the sender persona's row state is not controlled, so the case passes by accident of harness settings. ### F. Where this lands in the new core

Notifications are the registry-driven slice of rebuild slices 8–9 ("threads, notifications, activity"): a `notification_kind` registry with, per kind, its recipient rule (member / admin / lead / single actor / platform role), its scope policy, its settings key and its channel set — the table above is that registry written out. Three things found here should shape the model: (1) recipient resolution is one pipeline (NTF-10) and every kind must be in it or in the explicit bypass list — the five "fixed-channel / bypass" kinds (NTF-27, 28, 35, 56 receipt, 67) are the exceptions to encode, not to forget; (2) the suppress-on-replacement rule (NTF-32/33/66) and the actor-exclusion exceptions (NTF-16) are product rulings that must be first-class flags on the kind, not adapter code; (3) the chat digest (NTF-70..77) is a scheduler, not a notification kind — the new core keeps the four-track debounce as its own component feeding two kinds, with Redis state as a hint only. Settings become one row per kind per user with per-channel booleans and mandated defaults carried by the registry, so "defend on read" (NTF-05) disappears. Email subjects, push copy and windows are rebaseline rows, not rules.
