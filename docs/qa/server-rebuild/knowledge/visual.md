# Visuals — avatar, banner and card images — behaviour knowledge

_Extracted 2026-11-06 from three sources: server develop @ `eeecf9ddb` (Release/79) code + `schema.graphql`; the legacy server-api suite (`server-api/src/functional-api/visual/`, 2 files, 14 cases = 14 test blocks, 0 skipped) plus the visual cases of `storage/uploads` and `configuration/banner-visual-constraints` (listed, cross-referenced); the specs, issues and docs listed in § Sources. Scope: the visual slots every profile carries (avatar, banner, card, wide banner, whiteboard preview, media-gallery image and video), their allowed formats and sizes, what an upload does to the image, the adjustable banner shape, default and re-hosted avatars. Who may read the image **bytes** is the storage area (matrix `document`, crosscheck F1/F11) and is cross-referenced, not re-derived; media-gallery framing behaviour is CAL-40. WHAT and WHY only — no mutations, fixtures or request params. Status legend: **proven** = a green legacy case asserts it; **untested** = code and/or spec only, no case; **disputed** = sources disagree, see § Findings; **unknown-why** = the rule holds but no source states the reason — the reviewer fills the why or writes "unknown, ask product". Evidence paths are relative to the server repo unless prefixed `test ›` or `spec ›`. The extraction notes with every file:line are in `visual-dossier.md`._

_Review load: 8 findings · 2 unknown-why rows · 6 untested rows (gaps) · 27 constants to tick · 5 open questions. ## Where this lands in the new core

A visual is a typed image slot on the `space` document and on the `post` kinds (the catalogue's SP-2 "space document; file container blobs" and CT-9 "content-addressed blobs; upload by signed token to the file container"). Every rule above stays a behaviour; what changes is where the limits live. Three facts found here should shape the model: (1) the limits are **denormalised per row today** and have needed three data migrations for one slot kind (VIS-02) — the new core should keep limits on the kind (one table or constants) and store on the slot only what the user chose: the image blob, the alternative text and, for the banner, the chosen ratio; (2) the real image shape is decided by the file container after re-encoding (VIS-06/07/08) — keep "measure after canonicalise, then validate, then delete on refusal" as one transactional step in the file container rather than a server-side compensation; (3) the default avatar and the external-host allowlist (VIS-12/13) are a sign-up concern that should move with identity resolution, and the declared-type check (F-3) should disappear in favour of the sniffed type only. The adjustable banner (VIS-09/10/11) is the one piece of product logic: default 10, range 6–10, pixels win on upload — it belongs on the space document as a typed column. Error texts are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **Two legacy suites disagree on the banner default ratio (VIS-03/10).** Code: `visual.constraints.ts:54` `aspectRatio: 10` (PR #6452). Tests: `visual/banner-aspect-ratio` and `space-banner-constraints › TC-01` pin 10 (the latter notes it "caught the 6 → 10 move on the 2026-09-03 nightly"); `configuration/banner-visual-constraints › TC-03` still pins `aspectRatio: 6`. Spec: client-web#10178 AC "10:1 instead of 6:1"; the approved client plan predates #6452 and says "= 1200/120/6/6/10". Ruling: rebaseline TC-03 to 10 (configuration area); no behaviour question.
2. **The format allowlist is unproven and the one case named for it tests something else (VIS-05).** `storage/uploads › should not upload unsupported file type` uploads a 1299 px PNG to an avatar slot and asserts the **dimension** refusal. No case anywhere sends a non-image or an unlisted image type. Ruling: add a type-refusal case (and rename the storage case) — gap, not a product decision.
3. **Declared type vs real type (VIS-05).** Code: the server checks the client-declared MIME against the visual allowlist (`visual.service.ts:270-296`); the file service sniffs the content against the **bucket** allowlist, which includes every document type (`mime.file.type.ts:17-20`). A PDF declared as `image/png` passes the server check, is accepted and written by the file service, and is refused only by "Image dimensions missing from upload response" — then deleted. Fail-closed, but the file is written first and the message is misleading. Test/spec: none. Ruling: pass the visual allowlist to the file service as the override (as the Collabora path does) so the content is refused before it is stored.
4. **Ratio column cannot hold the media-gallery range (VIS-16).** Code: `aspectRatio` is `decimal(3,1)` ("< 99.9"), while MEDIA_GALLERY_IMAGE allows a ratio up to 100 and an upload computes `width / height` unbounded (an 8000 × 1 image → 8000.0). Test/spec: none. Ruling: clamp or widen the column; confirm live whether such an upload errors.
5. **Re-hosted avatars are declared PNG whatever they are (VIS-12).** `avatar.creator.service.ts:119-132` hard-codes `image/png` (TODO #4459); the stored row carries the sniffed type, but the file is named `avatar` with no extension and the server-side allowlist check is nominal. Ruling: harmless today (the file service sniffs); tidy when the file container owns typing.
6. **Error texts embed dynamic values (VIS-06/09).** `Upload image has a width resolution of '1299' …` and `Aspect ratio '5.9' …` contradict the repo rule against dynamic data in exception messages; two legacy cases pin substrings of them (`1200`, `not in the allowed range of 6 - 10`). Ruling: when the messages are cleaned, rebaseline those assertions; not a behaviour change.
7. **`updateVisual` accepts any address (VIS-09).** Code: `uri` is required and written verbatim (`visual.service.ts:73`) with no check that it is an Alkemio document or even a URL; the test re-sends the current uri "or it fails at variable coercion before validation is reached". A holder of "update" on a slot can point it at an external image or an empty string. Creation-time addresses are checked (VIS-13), updates are not. Test/spec: none. Ruling: validate (Alkemio document only, or allowlisted hosts) or document it as intended for the migration/import tooling.
8. **SVG is an allowed visual format but is excluded from conversation uploads as active content (VIS-05).** `mime.file.type.ts:28-32`: "SVG can carry active content, so it is not offered for member-to-member upload" — yet every profile slot accepts `image/svg+xml` and file-service passes SVG through unprocessed (VIS-07). Ruling: one policy for SVG (serve as attachment everywhere, or drop it from the visual list).

## Gaps (no legacy case)

Untested rules by id: VIS-07, VIS-12, VIS-13, VIS-14, VIS-15, VIS-18; plus the untested clauses of VIS-01 (every owner but the space), VIS-04 (every refusal — member, lead, non-member, anonymous on a space slot; another user on a user avatar; a non-admin on an organisation avatar), VIS-05 (any type refusal), VIS-08 (previous image deleted only within the same bucket; same-bytes re-upload reuses the file), VIS-16 (add/remove, video format refusal), VIS-17 (no delete; lengths).

- A HEIC upload end to end: accepted, stored as JPEG, measured after rotation, metadata gone (001 SC-001/002/004).

- An avatar/card/wide-banner/preview upload at its own bounds (only the banner's 1200 floor is proven; the avatar's 190–410 only via the 1299 refusal).

- Creating a space whose request supplies visual addresses outside Alkemio (ignored) or inside Alkemio (copied into the new bucket).
- Alternative text persisted and read back; the 120-character limit.
- Fixed-shape kinds refusing a ratio change (only the banner range is proven).
- Who can read a private space's slot metadata and image bytes (F1/F11 — storage).
- The media gallery: add, upload, order, remove (CAL-40 has no server-api case either).
