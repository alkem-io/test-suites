## Where this lands in the new core

The platform singleton dissolves into the briefing's ops namespace and the `viewer` slice: `metadata`/`configuration`/`latestReleaseDiscussion` are read-only platform facts served by the gateway (PLT-02/03 and `configuration.md`), the settings pair becomes a small `platform_setting` record whose readers and writers are decided explicitly rather than inherited from an unguarded field (PLT-10…14, F-1), the well-known-VC map becomes a typed reference that must point at an existing VC (PLT-06, F-4), and the per-family privileges of PLT-21 become capability-ledger rows with no cascade to "reset" (PLT-20 disappears with the stored policies). Three facts here should shape the core: (1) the root's fields are not gated by the platform policy today — whatever the new core publishes at its root must declare per field who may read it, because the matrix's `platform` row describes a policy nothing on the root consults; (2) the blacklist is a cross-service contract (PLT-14) — the notifications service's read of it must be a named integration, not an assumption; (3) the MCP containment rules (PLT-30…34) are the one proven slice here and belong with the 038 lifecycle, not with the platform root — keep them together when the areas are re-cut (F-6). Error texts are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **Platform settings, including the notification e-mail blacklist, are readable by anonymous (PLT-01/10).** Code: `settings` is a plain field on the `Platform` type with no privilege decorator and no `grantAccessOrFail`; the root query is unguarded. Matrix: the stored platform policy grants `read` to content-full-access only (anonymous `·`), so the matrix cell and the wire disagree. Test: `a10.ts` reads the settings as the settings admin only; no case reads them anonymously. Spec: 019 FR-005 wants the list "returned so downstream notification services can fetch the authoritative list" — it does not say to whom. Ruling: a list of real e-mail addresses served to the public is a privacy exposure — gate `settings` (settings admin, or at least registered) or confirm it is public by design.
2. **`platform.roleSet` is served without a privilege check (PLT-01).** Code: resolve field with the comment "TODO: protect with privilege..."; the role set's own fields carry their guards (matrix `platform/role-set` read `CTS` for anonymous). Ruling: harmless today (the child fields gate), but the TODO should be closed or the field documented as open.
3. **Nothing in the server consumes the blacklist or the iframe allow-list (PLT-14).** Code: the only reader is the initialiser. Spec 019: suppression lives in "downstream notification microservices". Test: none proves an e-mail on the list is not sent to. Ruling: route to the notifications table to confirm the notifications service reads `platform.settings.integration.notificationEmailBlacklist` and that a case exists; otherwise the setting is decorative.
4. **A well-known mapping accepts any UUID (PLT-06).** Code: `setMapping` upserts whatever id it is given; `a10.ts` says "the server does not resolve it". Spec: none. Ruling: validate that the id is a virtual contributor (the guidance chat would otherwise point at nothing), or record the rule as accepted.
5. **Settings refusals are plain `Error`s (PLT-13).** Code: wildcard, duplicate, cap and not-listed refusals throw `Error`, so the client receives `UNSPECIFIED` 99999 with the message — and, outside production, a stack trace. Spec 019 FR-003/FR-006 asks for "actionable feedback" / "a clear validation error". Ruling: make them `ValidationException`s (12xxx); the stack part is server#6663, never a new issue.
6. **The `platform/` test folder is not about the platform.** Test: the only file is 038's US3 containment suite (plus a `.gitkeep` whose name starts with a space); none of PLT-01…25 has a case here, and the suites that do cover them live under `platform-roles/` and `communications/`. Ruling: when the areas are re-cut, move the seven cases to an MCP area and let this table's gaps become the platform area's backlog.
7. **Two 038 acceptance clauses are not asserted (PLT-32/33).** Test: AS5 checks status and liveness but never reads the audit row that should show the administrator acted; AS6 uses a random UUID and says so — it does not prove that a system actor's key is unreachable. Spec 038 AS5/AS6 require both. Ruling: accept the server unit test for the predicate and add an audit read-back, or mark both clauses as known gaps.
