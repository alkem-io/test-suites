## Where this lands in the new core

The language is a two-column user preference and stays one: `user_preference.language` (nullable, one of the supported codes) and `language_offer_answered` on the `viewer`/user record, read through the `viewer` slice rather than `lookup.user.settings`; the supported set is a static enum in the core, the eligible list and the default remain deployment configuration exposed on the public config read (LNG-02). The invitation suggestion is a nullable column on the invitation row (one per invitation, LNG-10) and the seeding (LNG-12) is a registration-time step on the new core's "finalize registration" path — it must keep the three guards (fresh account only, eligible at that moment, latest-created wins) and must run before the first authenticated query. Two things found here should shape it: (1) who may write another user's preference should be an explicit rule, not an inherited cascade (F-1); (2) the only server-side consumer besides the client is the office-document editor (LNG-15) — notifications still ignore the setting (LNG-14), so e-mail localisation is a new-core capability, not a port. Error texts are rebaseline rows, not rules.

## Findings (sources disagree, or likely defect)

1. **Platform content-full-access can set any user's language and latch their answer (LNG-09).** Code: the write is gated on UPDATE of the user, which the root rule cascades to content-full-access (access matrix `user`: `update` CT for PCFA). Test: only a plain registered user is proven refused. Spec 029: the setting is the user's (FR-008/011); no admin write is described. Ruling: is a content role meant to change a person's interface language (and silence their offer), or should the write be self-only like the latch suggests?
2. **The latch can never be reset, by anyone (LNG-06).** Code refuses `false` for every caller. Spec: by design (FR-022). Data risk: a support request "show me the banner again" or a mis-recorded decline has no remedy but a direct database edit. Ruling: accept, or give the users-admin a reset.
3. **Eligible and default are unrelated settings (LNG-02).** Nothing stops a deployment making the default eligible (then "stored = suggestion" and "showing the fallback" are indistinguishable — the suite guards for it) or leaving `LANGUAGE_ELIGIBLE` empty without any log (the kill switch warns about unsupported entries only). Ruling: document the intended relation; add a startup log for the empty list.
4. **Regional codes are folded only on the client (LNG-01).** The server accepts bare codes; a stored `nl-BE` is "not supported". 029 FR-003 is client-side detection. Ruling: fine as is, or accept regional variants server-side when the eligible list grows.
5. **Every answer to the banner re-applies the user's whole authorization policy (LNG-09).** "For simplicity if a setting is updated we will reapply the authorization policy" — a full policy rewrite for a one-flag change; harmless for correctness, a cost at scale. Ruling: none needed for the knowledge; note for the new core.

## Gaps (no legacy case)

Untested rules by id: LNG-14 (e-mails stay in the default), LNG-15 (Collabora language), plus the untested clauses of LNG-01 (the exact six supported codes), LNG-02 (unsupported eligible entry dropped; unsupported default → English), LNG-08 (self read), LNG-11 (empty eligible list refuses every suggestion), LNG-12 (latest-created wins; "no longer eligible" skipped; existing language or answer not overwritten by a suggestion).

Behaviours the area has that neither reading nor tests pinned down:
- Changing a stored language to another supported one (every case writes once from null).
- A user who answered the offer anonymously and then registers (029 FR-013c — client carries it; the server sees a plain write).
- The Kratos sign-up path (not the admin `createUser`) seeding the language on a live stack.
- The organisation role-set invite path carrying `suggestedLanguage` (062 suite reads it back; seeding from an organisation invitation not asserted).
- A suggestion on an invitation to an existing user who never chose: the client offers it (DL-6); the server stores it on the Invitation only.
- `languageOfferAnswered` for a user created before the feature (migration leaves `false`; the client's DL-3 reconciliation decides) — no server case.
- A platform users admin reading, and being refused to write, another user's language.

## Open questions (could not be determined from the three sources)

1. **Does the Kratos sign-up path seed identically.** The suite registers through `createUser` and relies on the same `finalizeUserRegistration → processPendingInvitations → seedLanguageFromInvitation` chain; the real sign-up path was not exercised. A live Kratos registration with a pending suggestion settles it.
2. **Is the Collabora `lang` asserted anywhere.** `collabora/*.it-spec.ts` was not opened for a `lang`/language assertion; LNG-15 is untested until checked.
3. **Two eligible suggestions for one address.** The "latest-created wins" rule needs two role sets and two eligible languages (the config has one); the plan's gap table defers it to server unit tests — confirm those exist in server#6299 and are green.
4. **Is anyone meant to set a user's language on their behalf (F-1).** Product/support question; the code admits content-full-access by inheritance only.
