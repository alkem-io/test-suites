Coverage evidence = test-suites `origin/develop` @ `015bfeea1`: every root field is traced to the lib operations that use it and, through imports, to the server-api spec files and client-web spec files that reach it (`knowledge/_tools/` style tooling; see `root-fields.md` for the per-field trace). Client UI verdicts are the audit's (`../client-net-audit/`). "Lands in the new core" is from the architecture deck's "what goes where" tables. Verdicts are per feature and hand-assigned from the evidence columns._

**How to read a row.** *Legacy surface* counts the root fields the feature owns. *API reach* is how many of them are named by at least one server-api spec file or by a helper that spec imports, never counting what the lib alone does for it. It is still an upper bound on assertion coverage (a field named in a precondition counts, and the platform-roles capability table names most mutations for its gate checks); the W1 documents are the lower bound. *UI* is the audit journey verdict. *Harness use* is how many client-web spec files call any of the fields through the lib for preconditions or read-backs. *API areas* lists the server-api areas whose spec files reach any field, with the distinct file count. *Verdict*: **full** = API and UI prove the behaviour; **partial** = one side proves it or the proof is thin; **absent** = no proof on either side; **dead-by-design** = the rebuild drops it and it belongs on the expected-loss list.

## What this changes in the plan

- **W2 journey list is now evidence-backed.** The absent and partial rows in slices 4–5 and 6–7 are the ranked 12 journeys, in the same order; nothing in the matrix argues for a different order. Two additions surface: task boards (CT-8) and community guidelines (SP-10) have zero proof anywhere and are cheap UI cases.
- **W1 gets a lower-bound target per feature.** Each row's API reach says which fields the specs touch; W1 reads those cases and writes the rules. Fields reached by no spec (listed per row) are rules that must come from the product, not from tests — flag them in each area document.
- **W4 expected-loss list starts here.** The dead-by-design rows (MB-6 user groups, MB-9 policy resets, CM-6 admin communication ops, OP-3 subscriptions, LI-1 license resets) are the first entries for decision 8.
- **Rebaseline candidates are named.** Pagination cursors (OP-2), calendar containers (CT-10), activity grouping (CT-12), orphan oracle (SP-6), sidebar defaults (SP-9).
